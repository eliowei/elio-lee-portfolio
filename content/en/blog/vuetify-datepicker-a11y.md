While reworking a Vue 3 project to accessibility standards, I ran into a problem the component library couldn't solve: Vuetify's date picker couldn't be fully operated with the keyboard, and screen reader announcements were incomplete.

Date fields appear in several forms, so I turned the solution into a shared mixin, so that each page doesn't have to implement it again.

## First, list what users need to be able to do

Instead of fixing issues one by one, I first listed how someone using only a keyboard would pick a date:

| Key | Expected behaviour |
|---|---|
| Arrow keys | Left/right moves one day, up/down moves one week |
| Enter | Selects the date and returns to the input |
| Escape | Closes the picker and returns to the input |
| When switching month or year | Focus moves to the matching item in the list, and returns to the date after choosing |

This table also served as the acceptance criteria.

## Arrow keys: move the date, not the DOM

Which date is adjacent shouldn't be decided by finding the neighbouring button, because when crossing months that button may not exist. Converting keys into a number of days and letting `Date` handle month and year boundaries keeps the logic much simpler:

```js
const OFFSETS = { ArrowLeft: -1, ArrowRight: 1, ArrowUp: -7, ArrowDown: 7 }

function moveDate(current, key) {
  const next = new Date(current)
  next.setDate(current.getDate() + OFFSETS[key])
  return next
}
```

Dates outside the selectable range don't move; otherwise the caller updates the view and moves focus.

## Focus management: when the view changes, focus has to follow

This was the most time-consuming part. After choosing a month, the month list is replaced by the date grid; the button that had focus disappears, focus falls back to the start of the page, and keyboard users are effectively lost.

So for every view change, where focus goes has to be decided explicitly:

- Opening the month or year list: focus the item containing the current date.
- After choosing a month or year: return to the date grid, looking in order for the same date, the selected date, today, and only then the first available date.
- Closing with Enter or Escape: return to the original input.

Arrow keys in the month and year lists need separate handling too, because they are laid out in several columns: up and down have to skip a whole row's worth of items, not move by one.

## Screen reader labels: filling them in with MutationObserver

Date buttons need a full name so the screen reader can announce something like "Monday, 2 November 2026". But these buttons are generated by Vuetify and re-rendered when the month changes, so setting them once on open isn't enough.

My approach was to watch the picker for changes and add an `aria-label` only to buttons that don't have one yet:

```js
const WEEK = ['日', '一', '二', '三', '四', '五', '六']

function labelDays(picker) {
  picker.querySelectorAll('.v-date-picker-month__day button').forEach((btn) => {
    const iso = btn.closest('.v-date-picker-month__day')?.dataset.vDate
    if (!iso || btn.hasAttribute('aria-label')) return
    const d = new Date(iso)
    btn.setAttribute('aria-label', `${d.getFullYear()}年${d.getMonth() + 1}月${d.getDate()}日 星期${WEEK[d.getDay()]}`)
  })
}

const observer = new MutationObserver(() => labelDays(picker))
observer.observe(picker, { childList: true, subtree: true })
```

(The labels are in Chinese because the site is in Chinese.) Remember to call `disconnect()` when the picker closes, or the observer stays in memory. "Only label buttons without a label" isn't a redundant check either: the callback itself modifies the DOM, and rewriting every label each time easily leads to unnecessary repeated work.

## Verify with NVDA, not just by reading the code

Writing an `aria-label` doesn't mean it is read correctly. After the changes, I actually ran NVDA and went through the whole flow with only the keyboard: opening the picker, moving between dates, switching month and year, selecting and closing, checking that the focus position and announcement were as expected at every step.

## What I learned

- A component library doesn't mean accessibility. It saves a lot of work, but until you actually walk through the flow, you can't assume it handles everything.
- Accessibility isn't just adding attributes; focus management is the core of the keyboard experience.
- This approach depends on Vuetify's class names and DOM structure and may break on upgrade, so it has to be verified again after every upgrade.
