# Vue のプロジェクト構成からフロントエンドアーキテクチャの設計へ：プロジェクトはどこまで細かく分けられるのか

Vue を学び始めたときは、たいてい基本的なプロジェクト構成から始めます：

- `components/`：コンポーネントを置く
- `views/` または `pages/`：ページを置く
- `composables/`：再利用できるロジックを置く
- `services/`：API リクエストを扱う
- `stores/`：グローバルな状態を管理する
- `utils/`：共通のユーティリティ関数を置く

開発を始めたばかりのプロジェクトなら、この構成でたいてい十分です。

しかし機能が増えるにつれ、プロジェクトはいくつかのページとコンポーネントだけでは済まなくなり、さまざまな業務モジュール、データ管理、状態の処理、ページをまたいで共有するロジックが少しずつ現れてきます。

そうなると、単純に技術の種類で分類するやり方では、次のような問題にぶつかり始めることがあります：

- ある機能のコードがさまざまなディレクトリに散らばる。
- ひとつのページのロジックがどんどん複雑になる。
- 共通コンポーネントと業務コンポーネントの境界があいまいになる。
- 機能同士が互いに依存し始める。
- ひとつの機能を変えると、ほかの場所も同時に直す必要が出てくる。

そこで私は考えるようになりました：

**フロントエンドのプロジェクトは、どの程度まで分割すべきなのか。そして、ある機能を独立して管理する価値があるかどうかを、どう判断すればよいのか。**

この記事では、Vue のよくあるプロジェクト構成を出発点に、実際のプロジェクトで観察したさまざまな構成の仕方を整理し、さらに Feature、Component、Composable、Service、Store の責任と、モジュールを分割するときに考えるべきことを掘り下げます。

## 1. 学習段階でよく見る Vue のプロジェクト構成から始める

Vue のプロジェクトの初期は、たいてい技術的な責任で分類する方法を取ります：

```text
src/
├── assets/
├── components/
├── composables/
├── router/
├── services/
├── stores/
├── utils/
├── views/
├── App.vue
└── main.ts
```

この構成にはいくつかの利点があります：

1. わかりやすい：どのフォルダーにも明確な用途がある。
2. 探しやすい：コンポーネント、API、状態を直したいとき、対応するディレクトリにすぐたどり着ける。
3. 初期の保守コストが低い：小さな機能ごとに余計なディレクトリを作る必要がない。

しかしプロジェクトの規模が大きくなると、別の状況にぶつかることがあります。

たとえば：

```text
components/
├── Button.vue
├── UserTable.vue
├── UserForm.vue
├── PermissionDialog.vue
├── MapToolbar.vue
└── ReportChart.vue

composables/
├── useAuth.ts
├── usePermission.ts
├── useMap.ts
├── useReport.ts
└── useUser.ts
```

すべてのコンポーネントと Composable が技術の種類ごとにまとめて管理されています。

これ自体は間違いではありませんが、機能が増えてくると、開発者はある機能の流れ全体を理解するために、いくつものディレクトリを行き来して探す必要が出てきます。

たとえば会員管理の機能を直したいときは、次のものを同時に見つける必要があるかもしれません：

- 会員関連のコンポーネント
- 会員データの処理ロジック
- 会員の API
- 会員の状態管理
- 会員の型定義

これらのコードはどれも同じ機能に属しているのに、別々の場所に散らばっています。

そのためプロジェクトの規模が大きくなったら、業務の機能に沿ってコードを組織し直すべきかを考え始める必要があります。

## 2. 実際のプロジェクトで観察したさまざまな構成の仕方

規模の異なる Vue のプロジェクトに実際に触れてみて、プロジェクトの構成の仕方は 1 つだけではないとわかりました。

`features/` を主な機能の分類にしているプロジェクトもあれば、`modules/` を使っているものもあり、技術的な責任を中心にした共通ディレクトリを残しているものもあります。

以下は観察した構成を抽象化し、フォルダーの階層だけを例として残したもので、特定のプロジェクトの完全なディレクトリを表すものではありません。

### 構成例 A：Feature を中心に機能をまとめる

```text
src/
├── app/
│   ├── pages/
│   ├── layouts/
│   └── router/
│
├── features/
│   ├── auth/
│   ├── permission/
│   ├── member/
│   ├── map/
│   └── workflow/
│
├── components/
│   ├── common/
│   ├── table/
│   ├── form/
│   └── map/
│
├── composables/
├── services/
├── stores/
├── constants/
├── types/
├── utils/
└── styles/
```

この方法では、独立した業務上の責任を持つ機能を `features/` に集めます。

それぞれの Feature は、実際の必要に応じて次のものを自分で管理できます：

- Components
- Composables
- Services
- Stores
- Types

たとえば権限に関するコンポーネント、ロジック、データ処理を `permission/` にまとめれば、すべてをグローバルなディレクトリに散らばらせる必要はありません。

そして `components/`、`composables/`、`services/` などのディレクトリは、機能をまたいで使う共通の機能のために残しておきます。

### 構成例 B：Module を中心に機能をまとめる

```text
src/
├── app/
│   ├── layouts/
│   └── router/
│
├── pages/
│   ├── home/
│   ├── system/
│   ├── report/
│   └── profile/
│
├── modules/
│   ├── auth/
│   ├── dashboard/
│   ├── workflow/
│   └── map/
│
├── components/
│   ├── base/
│   ├── responsive/
│   └── ui/
│
├── composables/
├── services/
├── stores/
├── constants/
├── types/
├── utils/
└── styles/
```

この方法では、ページと機能モジュールを分けて管理します。

`pages/` は主にページの組み立てを担当し、`modules/` は独立した機能上の責任を持つモジュールを管理します。

たとえばページはさまざまなモジュールを組み合わせて、ユーザーの一連の操作の流れを表現できます。

さらにこうした構成では、PC 版、モバイル版、レスポンシブ対応の必要に応じて、Layout やページの構成の仕方をさらに分けることもあります。

### 2 つの方法の違いは何か

| 比較項目 | 構成 A | 構成 B |
| --- | --- | --- |
| 主な分類 | Feature | Module |
| ページの管理 | app/pages にまとめる | 独立した pages |
| 機能の管理 | features | modules |
| 共通コンポーネント | components | components |
| 共通ロジック | composables、services | composables、services |
| 構成の考え方 | 機能中心 | ページと機能を分けて管理 |

どちらが絶対に優れているということはありません。

特に説明しておきたいのは、`Feature` と `Module` は決まった標準的な違いを持つ 2 つのアーキテクチャパターンではなく、Vue が公式に定めたディレクトリ名でもないということです。チームによって、似た機能の構成の仕方を別の名前で表していることがあります。

そのため、ここで比べるべきなのは名前そのものではなく、次の点です：

- ページと機能モジュールがどう分担しているか。
- 機能のコードを誰が管理しているか。
- 共通の機能をどこに置いているか。
- モジュール間の依存関係をどう作っているか。

本当に注目すべきなのはフォルダーの名前ではなく、各モジュールに明確な責任があるか、そしてモジュール間の依存関係が妥当かどうかです。

## 3. Page、Section、Component、Feature の責任の違い

プロジェクトを分割し始めると、まずぶつかるのが次の問題です：

**何を Page に置くべきか。いつ Component に分けるべきか。そしていつ Feature として独立させる必要があるのか。**

私はまず、それぞれの責任から理解するようにしています。

### Page：ページを組み立てる

Page は通常、ひとつのルート、つまりユーザーがアクセスできるページに対応します。

主な仕事は次のとおりです：

- さまざまなコンポーネントを組み合わせる。
- ページ単位のデータを管理する。
- ページへの出入りに関する処理を行う。
- さまざまな機能モジュールをつなぐ。

Page がすべての業務ロジックを担う必要はありません。

Page の中に大量のデータ処理、状態管理、操作ロジックが含まれているなら、責任の一部を適切なモジュールや Composable に移すことを検討できます。

### Section：ページの区画を担う

Section は通常、Page の中で独立した表示目的を持つ区画です。

たとえば：

- 検索エリア
- 統計情報エリア
- データ一覧エリア
- グラフ表示エリア

ページの内容が複雑になったら、Section で区画を分けることで Page を読みやすくできます。

ただし Section はすべてのプロジェクトで必ず採用すべき階層ではなく、分けるかどうかはやはりページの複雑さ次第です。

### Component：再利用できる UI を担う

Component は主に画面の表示とユーザーの操作を担当します。

たとえば：

- Button
- Dialog
- Table
- Form
- Card

Component は単純な UI 部品であることもあれば、ある程度の操作ロジックを含むこともあります。

しかしコンポーネントが一連の業務フローまで担い始めたら、それがどこかの Feature に属するべきではないかを考え直す必要があります。

### Feature：完結した業務機能を担う

Feature は単にコンポーネントをひとまとめにしたものではなく、明確な目的を持つ機能をまとめて管理するものです。

たとえば会員管理の機能には、次のものが含まれるかもしれません：

- 会員一覧
- 会員情報の編集
- 会員の状態管理
- 会員関連の API
- 会員データの型

これらは技術の種類としてはばらばらですが、どれも同じ業務機能のためにあるので、同じ Feature にまとめることを検討できます。

簡単にまとめると：

| 階層 | 主な責任 |
| --- | --- |
| Page | ページ全体を組み立てる |
| Section | ページの区画を整理する |
| Component | UI の表示と操作 |
| Feature | 独立した責任を持つ業務機能を管理する |

これらの階層は固定のルールではなく、コードを誰が担当すべきかを考えるための手がかりです。

## 4. Composable、Service、Store の責任をどう区別するか

コンポーネントと機能モジュールのほかにも、Vue のプロジェクトにはよく使うコードの整理の仕方がいくつかあります。

### Composable：再利用できるロジックをまとめる

Composable はふつう `use` で始まります。たとえば：

```ts
useAuth()
usePagination()
useWindowSize()
```

主な用途は Composition API のロジックをまとめ、さまざまなコンポーネントで再利用できるようにすることです。

Composable に入れるのに向いているものは次のとおりです：

- リアクティブな状態
- ライフサイクルの処理
- イベントの監視
- UI の操作ロジック
- 再利用できるインタラクションのロジック

ただし、すべてのロジックをグローバルな `composables/` に置くべきではありません。

ある Composable が特定の Feature のためだけにあり、その機能と密接に関わっているなら、その Feature の中に置くことを検討できます。

### Service：外部のデータやサービスとの連携を担う

Service は通常、API リクエストなど外部のシステムとのやり取りを担当します。

```ts
export const getMembers = () => {
  return api.get('/members')
}

export const updateMember = (id: string, data: unknown) => {
  return api.put(`/members/${id}`, data)
}
```

API リクエストをまとめて管理すれば、コンポーネントがリクエストの細かな処理を直接大量に抱えることを避けられ、データ連携の方法も保守しやすくなります。

Service は HTTP だけを扱うとは限らず、プロジェクトの必要に応じてほかの外部サービスとの連携も担当できます。

### Store：コンポーネントやページをまたいで共有する状態を担う

Pinia を例にすると：

```ts
export const useUserStore = defineStore('user', {
  state: () => ({
    user: null,
    permissions: []
  })
})
```

Store は、異なるコンポーネントやページの間で共有する必要のある状態の管理に向いています。

たとえば：

- ユーザー情報
- ログイン状態
- 権限データ
- グローバルな設定

ただし、すべての状態を Store に入れる必要はありません。

状態がひとつのコンポーネントの中でしか使われないなら、たいていは `ref()` や `reactive()` をそのまま使えば十分です。

### 3 つの違い

| 種類 | 主な責任 | よくある用途 |
| --- | --- | --- |
| Composable | 再利用できるロジックをまとめる | UI、リアクティブなロジック、ライフサイクル |
| Service | 外部サービスとの連携を扱う | API、データのリクエスト |
| Store | 共有する状態を管理する | ユーザー情報、権限、グローバルな状態 |

これらは互いに置き換えるものではなく、責任に応じて役割を分担するものです。

## 5. Feature-based Architecture と技術的な責任による分類の違い

前に挙げた 2 つの構成は、実は 2 つの異なる考え方を反映しています。

### 技術的な責任で分類する

```text
src/
├── components/
├── composables/
├── services/
├── stores/
├── types/
└── utils/
```

この方法は、コードの技術的な用途で分類します。

わかりやすく、規模の小さなプロジェクトに向いているのが利点です。

しかし機能が増えると、同じ業務機能のコードがさまざまなディレクトリに散らばることがあります。

### 業務の機能で分類する

```text
src/
├── features/
│   ├── auth/
│   ├── member/
│   ├── permission/
│   └── report/
│
└── shared/
    ├── components/
    ├── composables/
    ├── services/
    └── utils/
```

この方法では、まず業務の機能でモジュールを分け、それから各機能に必要なコードをまとめて管理します。

利点は、ある機能を直したいとき、比較的まとまった範囲の中で関連する内容を見つけられることです。

しかし新たな問題が生まれることもあります：

- Feature の数が多くなりすぎる。
- 機能の境界がはっきりしない。
- Feature 同士が互いに依存する。
- 同じ共通ロジックが何度も実装される。

そのため Feature-based Architecture とは、何もかも Feature に分けることではなく、どの機能が本当に独立して管理する価値があるかを見極めることなのです。

### Layered Architecture とは何が違うのか

また、Layered Architecture（レイヤードアーキテクチャ）という考え方もよく目にします。

これは主に、システム内の責任と依存関係に沿って層に分けるものです。たとえば：

```text
src/
├── presentation/
├── application/
├── domain/
└── infrastructure/
```

ひとまず次のように理解できます：

| 層 | 責任 |
| --- | --- |
| Presentation | ユーザーインターフェースと操作 |
| Application | アプリケーションの流れとユースケース |
| Domain | 中核となる業務ルール |
| Infrastructure | 外部サービス、データソース、技術的な実装 |

Feature-based Architecture と Layered Architecture は互いに排他的な設計ではありません。

前者は業務の機能に沿ってコードを組織する方向に、後者は責任と依存関係に沿って層に分ける方向に寄っています。

規模の大きなシステムでは、この 2 つの考え方を同時に取り入れることもあります。

ただし、すべての Vue のプロジェクトにこうした層構造を完全に導入する必要があるわけではありません。

プロジェクト自体に十分な複雑さがなければ、抽象化の層を過剰に導入すると、かえって理解と保守のコストが増えてしまいます。

## 6. 機能を Feature として独立させるべきかをどう判断するか

さまざまなプロジェクトの構成を整理してみて、これがいちばん考える価値のある問いのひとつだと思いました。

最初、私は直感的にこう考えていました：

ある機能が 2 か所以上で必要になるなら、独立させることを検討すべきだ。

この考え方は最初の判断の目安にはなりますが、実際には使われる回数だけで、その機能が Feature に向いているかを決めることはできません。

たとえば日付をフォーマットする関数は 10 個のページで使われているかもしれませんが、それ自体は単純なユーティリティ関数なので、`utils/` に置けば十分です。

逆に、ある会員管理の機能は今はひとつのページでしか使われていなくても、すでにデータ管理、状態の処理、操作の流れを一通り含んでいるなら、独立して管理する価値があるかもしれません。

そこで私は、次のような観点から判断しています。

### 6.1 利用範囲：複数の場所で使われているか

ある機能が 2 つ以上のページやモジュールで使われるようになったら、切り出して管理すべきかを評価し始めます。

たとえば：

```text
pages/
├── dashboard/
├── member/
└── report/
```

これらのページがすべて権限を判定するロジックを必要としているなら、権限に関する機能をまとめて管理すべきかを考えられます。

ただしこれは評価のための目安にすぎず、2 か所で使われているからといって必ず Feature を作るべきだという意味ではありません。

それが独立した機能上の責任を持っているかも確認する必要があります。

### 6.2 業務上の責任：明確で独立した目的があるか

コードが汎用的なユーティリティを提供しているだけなら、たとえば：

- 日付のフォーマット
- 数値のフォーマット
- 文字列の処理
- 汎用的な検証関数

これらはたいてい Feature として独立させる必要はありません。

しかしそれがひとつの完結した業務機能を表しているなら、たとえば：

- 会員管理
- 権限管理
- ログイン認証
- ワークフロー管理

関連する内容を独立した Feature にまとめることを検討できます。

これは分割するかどうかを判断するうえで、かなり重要な基準だと考えています。

### 6.3 データと状態：独自の管理の必要があるか

ある機能が独自のデータ、状態、操作の流れを持ち始めたら、独立して管理する必要があるかを検討する価値があります。

たとえば権限管理には次のものが含まれるかもしれません：

- 権限データの取得
- 権限の状態管理
- 権限ルールの判定
- 権限の変更操作

こうしたロジックが少しずつさまざまなページやコンポーネントに散らばっていくと、保守が難しくなることがあります。

まとめて管理すれば、権限に関する変更を追いやすくなります。

### 6.4 保守の必要：独立して修正・拡張する必要があるか

もうひとつ考えるのは、その機能に独自の変更の必要があるかどうかです。

たとえば権限のルールは、要件が増えるにつれて調整され続けるかもしれません。

修正のたびにさまざまなページを回って関連するロジックを探す必要があるなら、今の構成ではまとまりが足りないということです。

そのときは関連するコードを独立した Feature に整理すれば、今後の保守の範囲がはっきりします。

### 6.5 依存関係：分割して本当に結合度が下がるか

最後に、分割したあとの結果も考える必要があります。

Feature を作ったことで、かえって Feature 同士が互いの内部実装を大量に参照するようになったり、循環依存まで生まれたりするなら、その分割はアーキテクチャを本当には改善していないかもしれません。

たとえば、2 つの Feature の間に次のような依存関係ができたとします：

```text
member ──────> permission
   ↑               │
   └───────────────┘
```

これは `member` が `permission` に依存し、`permission` も逆に `member` に依存していることを表しています。

2 つの機能が互いの内部実装を直接参照していると、循環依存になる可能性があり、モジュール間の責任もあいまいになります。

そのときは責任の所在を考え直す必要があります。次のようなことを検討できます：

- 公開されたインターフェースを通じて必要な機能を提供する。
- ほかの Feature の内部実装を直接参照しない。
- 本当に共通の機能は Shared に移す。
- データと業務ロジックをどのモジュールが担当すべきかを改めて確認する。

### 私の Feature 分割の判断基準

ここまでの観点をまとめると、私は次のように判断しています：

| 判断の条件 | 私の対応 |
| --- | --- |
| 2 か所以上で使われている | 切り出すかの評価を始める |
| 独立した業務上の責任がある | 独立した管理を強く検討する |
| 独自のデータと状態がある | まとめて管理することを評価する |
| 独立した保守・拡張の必要がある | 分割を検討する |
| 分割するとかえってモジュールの依存が増える | 責任の境界を見直す |
| 汎用的なツールや単純な共通ロジックにすぎない | Shared や Utils に置けば十分 |

これらの条件を絶対的なルールとは考えておらず、評価の基準として使っています。

**私にとって、Feature として独立させる価値があるのは、いちばん多く使われているコードではなく、すでに独立した責任を持ち、独立して理解・保守・拡張される必要のある機能です。**

## 7. プロジェクトはどこまで細かく分けるべきか

さまざまな構成の仕方を理解したところで、もうひとつ問いが残ります：

細かく分ければ分けるほど、アーキテクチャは良くなるのか。

私はそうは思いません。

分割の目的はコードを理解しやすく保守しやすくすることであって、ディレクトリの数を増やすことではないはずです。

たとえば、単純な機能なら次のもので足りるかもしれません：

```text
features/
└── member/
    ├── components/
    ├── services/
    └── composables/
```

しかし小さな機能のためだけに、さらに何層ものディレクトリを作ったとしても：

```text
features/
└── member/
    ├── components/
    │   └── internal/
    │       └── shared/
    ├── application/
    │   └── use-cases/
    ├── infrastructure/
    │   └── repositories/
    └── domain/
        └── entities/
```

保守性が良くなるとは限りません。

どのディレクトリにも単純なファイルが 1 つあるだけで、責任が本当には分かれていないなら、探す手間が増えるだけかもしれません。

私は次のような要素を考えます：

1. 機能の複雑さ：分割が必要なほどのロジックがすでにあるか。
2. 責任の明確さ：それぞれのコードが異なる責任を持っているか。
3. 再利用の度合い：ほかの機能と共有する必要があるか。
4. 保守の必要：今後、独立して修正・拡張する可能性があるか。
5. 依存関係：分割することで結合度を下げられるか。

分割によって責任がより明確になり、依存関係がより単純になり、しかも理解のコストがそれほど増えないなら、その分割には価値があります。

## 8. 過剰な抽象化と結合の問題

プロジェクトのアーキテクチャを設計するときは、2 つの方向の両方に注意が必要だと考えています。

### 過剰な抽象化

コードをもっときれいにしたいと思うあまり、前もってたくさんの抽象化の層を作ってしまうことがあります。

たとえば：

- まだ重複する要件が出てきていないのに、先に共通モジュールを作る。
- ごく小さな機能まで複数のディレクトリに分ける。
- コンポーネントごとに独立した Composable を作る。
- あるアーキテクチャパターンに合わせるために、不要な中間層を増やす。

こうしたやり方が必ずしも間違いだとは限りませんが、抽象化そのものが実際の問題を解決していないなら、コードがかえって理解しにくくなることがあります。

### モジュール間の結合

もうひとつの問題は、モジュール間の依存関係です。

Feature ごとに独立したディレクトリがあっても、それらの間に結合がないとは限りません。

たとえば：

```text
features/
├── member/
├── permission/
└── workflow/
```

表面上は分かれているように見えても、`member` が `permission` の内部実装を直接参照し、`permission` も逆に `member` に依存していれば、循環依存が生まれる可能性があります。

そのため Feature を作ったあとも、次のことを考える必要があります：

- このデータはどのモジュールが持っているのか。
- この業務ロジックはどのモジュールが担当するのか。
- ほかのモジュールはどのような方法でそれを使うべきか。
- 切り出せる本当に共通の機能はあるか。
- 不要な双方向の依存が生まれていないか。

良いモジュールの境界とは、単にコードを別々のフォルダーに入れることではなく、機能同士に明確な責任と依存の方向を持たせることです。

### フォルダー構成はシステムアーキテクチャのすべてではない

これも、この記事をまとめながら特に気づいたことです。

フォルダー構成を見るだけでは、プロジェクトのアーキテクチャの質を完全には判断できません。

たとえば：

- フォルダーだけでは、実際の import の依存の方向はわからない。
- 状態が正しいモジュールで管理されているかは確認できない。
- データの流れが妥当かは判断できない。
- 循環依存があるかは確認できない。
- モジュールが本当に独立した責任を持っているかはわからない。

そのためディレクトリ構成は、プロジェクトの組織の仕方を理解するための出発点にすぎません。

本当にアーキテクチャを評価するには、やはりコードを読み、モジュール同士のやり取りを観察し、機能を変更したときにどこに影響するかを理解する必要があります。

## 9. 今回学んだこと

Vue を学び始めたときに触れた基本的なディレクトリ構成から、のちにさまざまなプロジェクトの構成の仕方を観察するまでを通じて、フロントエンドのアーキテクチャとは、単にフォルダーをいくつ作るかを決めることではないと少しずつ気づきました。

本当に考えるべきなのは次のことです：

- ある機能は誰が担当すべきか。
- どのロジックをまとめて管理すべきか。
- どのコードを共有するのが適切か。
- 機能同士はどのように依存すべきか。
- いつ分割すべきで、いつシンプルなままにしておくべきか。

また、`Feature`、`Composable`、`Service`、`Store` は、プロジェクトをアーキテクチャらしく見せるために存在しているのではないとも理解するようになりました。

それぞれに異なる責任があり、実際の必要に応じて使うべきものです。

特に Feature として独立させるべきかを判断するときは、あるコードが何回使われているかだけを見るのではなく、独立した業務上の責任、データ管理の必要、そして今後の保守と拡張の必要性まで考える必要があります。

私にとって、**良いプロジェクトアーキテクチャとは細かく分ければ分けるほど良いものではなく、すべてのコードに妥当な居場所があり、すべての機能を明確な責任の範囲の中で理解し保守できるものです。**

これが、単にフロントエンドの機能を完成させることから、プロジェクトの組織とエンジニアリングとしての保守を考えるようになって、フロントエンドのアーキテクチャ設計について一段深く理解できたことです。
