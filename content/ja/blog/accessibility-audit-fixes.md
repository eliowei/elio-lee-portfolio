これまでで最も長くかかった修正でした。Vue 3 + Vuetify のウェブサイトをアクセシビリティ検査に出す必要があったのです。プロジェクトの初期にはすでに台湾の自動検査ツール FreeGo で何度か検査と修正が行われていて、私が引き継いだのは人による検査の結果と、その後の差し戻しへの対応でした。何度も差し戻しを経て、ようやく A 等級の認証を取得できました。

最初は、アクセシビリティとは `alt` と `aria-label` を付けることだと思っていました。やり終えてみて、それはサイト全体の構造が問われるものであり、FreeGo のような自動検査ツールに通っても人による検査に通るとは限らないとわかりました。この記事では、修正した内容を問題の種類ごとにまとめます。

## セマンティクスと基本情報

### ページの言語

スクリーンリーダーは `lang` に基づいて読み上げる言語を決めます。プロジェクトのデフォルトの `en` のままだと、中国語の内容が間違った方法で処理されてしまいます：

```html
<html lang="zh-Hant">
```

### ページのタイトルはページに合わせて変える

シングルページアプリケーションでは、ルートを切り替えてもタイトルは自動では変わりません。ユーザーはページが変わったことを聞き取れないので、ルートにタイトルを設定し、まとめて更新するようにしました：

```js
{
  path: '/member-login',
  meta: { title: '會員中心 > 會員登入' },
}

router.afterEach((to) => {
  document.title = `${to.meta.title} | 網站名稱`
})
```

### 見出しの階層

これが最も差し戻しの多かった項目です。検査が見ているのは文書のアウトラインであって、文字の大きさではありません。

Vuetify の `text-h3` はスタイルにすぎず、本物の見出しにはなりません。見た目は見出しなのに実は `div` だった箇所や、文字を大きくするためだけに `<h1>` を使っていた箇所がたくさんありました。修正では、見た目と意味を切り離す必要があります：

```html
<!-- 意味はタグで、大きさは class で決める -->
<h1 class="text-h5">會員中心</h1>
<h2 class="text-h3">會員登入</h2>
```

原則は、1 ページに `h1` は 1 つ、階層を飛ばさないことです。

また `<h1 role="alert">` のような書き方も取り除きました。`alert` はスクリーンリーダーにすぐユーザーを遮らせるので、普通の見出しには適していません。

## 代替テキスト

代替テキストは、すべての画像に書けばよいわけではありません：

- **情報を持つ画像**：内容を説明する。
- **純粋な装飾の画像**：`alt` を空文字列にすれば、スクリーンリーダーは読み飛ばす。

```html
<!-- 変更前：スクリーンリーダーが意味のない内容を読み上げる -->
<v-img alt="登入頁插圖" src="login.svg" />

<!-- 変更後：装飾画像がユーザーの邪魔をしない -->
<v-img alt="" src="login.svg" />
```

これは直感とは逆です。`alt` を書かないことと `alt=""` は違い、前者はファイル名が読み上げられることがあります。

## リンクとボタンは目的をはっきりさせる

「ダウンロード」「<」「>」のような文字は、それだけ聞いても何をするのかまったくわかりません。ボタンには単独で理解できる名前が必要です：

```html
<v-btn icon="mdi-chevron-left" aria-label="上一項說明" />
<a href="manual.pdf" aria-label="下載手機版操作手冊 PDF">下載</a>
```

## フォーム

### 必須であることを伝える

赤いアスタリスクだけでは、スクリーンリーダーが読み上げるとは限りません。そこで「必須」をラベルの文字に含めました：

```html
<v-text-field>
  <template #label>
    <span>驗證碼(必填)</span>
  </template>
</v-text-field>
```

### ラベルとフィールドを関連付ける

すべてのフィールドに対応する `label` が必要です。認証コードのように、レイアウトの都合でラベルを省略したフィールドはすぐに指摘されます。

### 日付のフィールドはキーボードで操作できるようにする

Vuetify の日付ピッカーにはキーボード操作とフォーカス管理を補う必要がありました。これについては「Vuetify の日付ピッカーをキーボードとスクリーンリーダーに対応させる」に別にまとめています。

## キーボードのユーザー：スキップリンク

キーボードだけを使う人は、どのページでもメニュー全体を Tab で通り過ぎないと内容にたどり着けません。そこで各ページの最上部に、普段は隠れていて Tab でフォーカスしたときだけ現れるリンクを置きます：

```css
.skip-link {
  position: absolute;
  top: -100px;
}

.skip-link:focus {
  top: 0;
}
```

```js
function skipToMain() {
  document.getElementById('main-content')?.focus()
}
```

メインコンテンツには `tabindex="-1"` を付けないと、プログラムからのフォーカスを受け取れません：

```html
<main id="main-content" tabindex="-1">...</main>
```

## 導盲磚（アクセスキーによるナビゲーション）：領域へすばやく移動する

台湾のアクセシビリティ基準では、ページ上に「導盲磚」と呼ばれる `:::` の目印を置き、ショートカットキーで主要な領域に移動できるようにします。一般的な慣例は次のとおりです：

| ショートカット | 領域 |
|---|---|
| Alt + U | 上部の領域 |
| Alt + C | 中央のメインコンテンツ |
| Alt + Z | 下部の領域 |

実装には `accesskey` を使います：

```html
<a accesskey="C" href="#C" title="中間主要內容">:::</a>
```

構文は難しくなく、プロジェクトにも一部のページにはすでに導盲磚がありました。本当に時間がかかったのは、それを全ページにそろえることです。検査ではすべてのページに導盲磚が求められますが、既存のページはその要件を前提に設計されておらず、レイアウトの構造もまちまちだったので、共通コンポーネントを 1 つ追加して終わりというわけにはいきませんでした。

1 ページずつ調整するしかありませんでした。タイトル部分のレイアウトを変える必要があるページもあれば、位置指定で既存のレイアウトに収める必要があるページもあり、モバイル版で内容が押しつぶされないかにも気を配りました。さらに、導盲磚の位置とスタイルを各ページでそろえ、ユーザーがページを移るたびに探し直さなくて済むようにする必要もありました。

これだけで 20 個のファイルを変更しました。最初から上・中・下の領域を共通のページレイアウトに組み込んでいれば、1 か所を変えるだけで済んだはずです。操作説明にもショートカットキーをはっきり書いておかないと、ユーザーは使い方がわかりません。

## 今回学んだこと

- アクセシビリティは構造の問題であって、最後にいくつか属性を足せば済むものではない。対応が遅れるほど、直すページが増える。
- FreeGo のような自動ツールで見つかるのは問題の一部だけ。実際にキーボードとスクリーンリーダーで一通り操作してはじめて確かになる。
- 見た目と意味は分けて考える。見出しに見えるからといって、見出しであるとは限らない。
- 共通コンポーネントを先に正しく作れば、あとで直すページがずっと少なくなる。
- 差し戻しは悪いことではない。差し戻しの理由が、毎回どこに問題があるのかをはっきりさせてくれた。
