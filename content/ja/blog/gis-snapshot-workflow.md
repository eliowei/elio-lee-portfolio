業務で扱っている GIS 地図画面には、もともとスナップショットコードの機能がありました。特定の地図の表示状態を記録し、コードを入力すれば同じレイヤーと位置に戻れる機能です。

既存の地図画面を拡張する際、このスナップショット機能を新しい操作の場面に組み込む必要がありました。この記事では技術的な判断に絞り、実際の業務条件や画面の詳細は省いています。

私は主にフロントエンドの機能開発を担当しました。まず既存のコードを調べ、スナップショットコードがどう動くか、API がどんなデータを返すかを確認してから、操作画面と機能の流れを設計しました。

これはそのフロントエンド連携の記録です。使った技術は Vue、OpenLayers、REST API で、既存機能とデータの流れの理解に重点を置いています。

## まず、既存の機能がどう動くかを確認する

要件を受けたとき、最初に既存のスナップショット機能のコードを読み、地図の位置合わせとどうつながっているかを理解しました。

確認したのは次のような点です。

- 既存のスナップショット機能は、システム内でどう起動され、どんな流れで実行されるか。
- コードを取得したあと、どうやって地図を該当の表示に戻すか。
- 新しい要件で流用できる既存のロジックはどれか。
- 新しい操作を追加すると、既存のどの処理を通るか。

これらの関係がはっきりして初めて、既存のスナップショットの仕組みを新しい操作の場面につなげれば、作り直す必要がないと確認できました。

私にとってこの段階で時間がかかったのは、機能同士の関係を見つけることでした。ある関数が何をするかが分かっても、それがいつ呼ばれ、前後でどんなデータが必要かまでは分かりません。

## データが足りるか分からないときは、まず既存 API を試す

次に、新しい機能に必要なデータがどこから来るかを確認しました。

既存 API を繰り返し呼び出し、返ってくる内容を既存コードでの使われ方と照らし合わせて、各フィールドの用途を理解したうえで、そのデータが新しい要件を支えられるかを確認しました。

主に見たのは次の点です。

- 新機能に必要なデータがすでに返されているか。
- フィールドがもともと何を表しているか。
- 既存機能がそのフィールドをどう使っているか。
- 新しい流れに入れたとき、元の用途に影響しないか。

テストの結果、既存の返却フィールドで今回のフロントエンド機能に必要なデータを提供できると分かりました。

そのうえで PM と、既存 API を流用できるか、どんな影響があるかを相談し、既存のインターフェースでフロントエンド連携を完成できると確認しました。

**今回はフロントエンド連携のためにバックエンド API を追加で拡張しませんでしたが、事前のデータ確認は必要でした。** フィールドの値が使えるからとそのまま機能につなぐと、そのフィールドが本来何のためにあるのかを見落としやすくなります。

## 同じ要件でも、入口が違えば実行順序は同じとは限らない

連携を進めるうちに、操作の入口が違うと、必要なデータは似ていても、データを取得するタイミングやその後の処理の流れが同じとは限らないと分かりました。そのため API の返却内容を確認するだけでなく、データがいつ取得され、後続のコードがどう使うかも追う必要がありました。

入口ごとに次を確認しました。

1. 元の実行の流れ。
2. データの問い合わせがどのステップで起動するか。
3. 問い合わせの後にどんなデータ処理が走るか。
4. 新機能にどんなデータが必要で、後続の処理とどうつなぐか。

各入口の元の実行順序を確認してから、対応するロジックを調整し、問い合わせ、データ処理、関連機能が正しくつながるようにしました。

この過程で改めて意識したのは、**必要なデータの種類が似ていても、操作の流れが同じとは限らない**ということです。

既存システムに機能を足すときは、API が何を返すかを見るだけでなく、データがいつ取得され、後ろのコードがいつ使うかまで追う必要があります。

## 要件をフロントエンドの操作の流れに整理する

データと機能の関係を理解したら、次はフロントエンドの画面と操作方法の設計です。

既存機能とデータの出どころを確認したうえで、それらをユーザーが操作できる流れに整理し、関連する画面と機能を作りました。

- 要件に沿って新しい操作画面を設計する。
- 新機能に必要なデータを取得して処理する。
- 既存のスナップショットによる位置合わせ機能を組み込む。
- 入口ごとに実行順序を調整する。
- 新しい操作の流れを既存の画面に組み込む。

最初の実装が済んだら、PM と機能が要件を満たしているかを確認しました。

今回のフロントエンドの担当範囲は、要件の理解、データが足りるかの確認、そして機能を既存の流れにどうつなぐかの判断までを含みます。

## API を流用しても、フィールドの用途には注意する

既存 API を流用したことで、変更を主にフロントエンドに集め、バックエンドの拡張とそれに伴う連携作業を避けられました。

ただし、これは今後の要件でも既存のフィールドを優先して使えばよいという意味ではありません。フィールドの用途が要件に合っているか、将来保守しやすいかを見る必要があります。

たとえば次のような点です。

- フィールドの元の意味が、新機能に必要なデータと一致しているか。
- 新機能が、明確に取り決められていない返却形式に依存していないか。
- バックエンドがフィールドを変更するとき、新機能も使っていると気づけるか。
- 二つの機能が将来別の方向に進む場合、分ける必要があるか。

これは今回の経験から、今後さらに気をつけたい保守上の問題です。データがたまたま似ているだけで用途が違う場合は、バックエンドとよりよい方法を相談する必要があります。

## 何が改善され、何がまだ断定できないか

今回、既存のスナップショット機能とフロントエンドの新機能の連携が完成し、バックエンド API を追加で拡張せずに必要なデータを取得できることも確認できました。

既存の機能とデータを新しい場面で再利用でき、同じ機能を作り直さずに済みました。操作時間が実際に短くなったか、作業効率が上がったかは、今後の利用データがなければ確認できません。

また、バックエンド API を変更していないからといって、回帰テストが不要になるわけではありません。新しいロジックは既存の流れに入るため、入口ごとの動作、元の位置合わせ機能、データ不足や問い合わせ失敗時の処理は確認が必要です。

## 今回学んだこと

今回いちばん力を入れたのは、実装に入る前に、既存の機能、API のデータ、操作の順序を突き合わせることでした。

覚えておきたいポイントは次の通りです。

- **まず既存の流れを追う。** 関数が何をするかだけでなく、いつ実行され、どんなデータに依存するかも知る。
- **API を拡張する前に、まずデータを確認する。** 再利用できるかは、実際の返却内容とフィールドの用途で決まる。
- **入口ごとに確認する。** 似たデータの要件でも、実行の流れは別のことがある。
- **変更範囲が小さくても検証は必要。** 特に既存の流れに入るロジックは、新しい画面が正常かどうかだけでは足りない。

今回の機能拡張で、機能追加はゼロから作るとは限らないと改めて理解しました。要件から出発し、既存システムの実行の流れを読み解き、再利用できる機能とデータを確認する。そうすることで、変更範囲と実装方法をより根拠をもって決められます。
