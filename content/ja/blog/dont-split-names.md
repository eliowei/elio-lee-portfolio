今回の要件は、会員登録の氏名を台湾原住民族の名前に対応させることでした。原住民族の名前は、1 文字の姓とそれに続く名に分けられるとは限らず、中点 `·` でつなぐものもあります。そこでフォームは「氏名」の 1 フィールドに変えましたが、バックエンドのデータは相変わらず `first_name` と `last_name` の 2 つの値を必要としていました。

最初に思いついたのはごく自然な方法で、ユーザーが入力した氏名を分割する関数を書くことでした。そして 2 か月後、会員登録のフローからこのロジックを削除しました。

## 当時の分割ルール

よくある氏名の形式をもとに、いくつかのルールを書きました：

1. 中点 `·` か空白があれば、最初の記号で区切る。
2. 先頭が漢字なら、最初の 1 文字を姓、残りを名とする。
3. それ以外は、全体を 1 つのフィールドに入れる。

コードにするとだいたいこうなります：

```js
function splitName(name) {
  const trimmed = name.trim()
  const index = trimmed.search(/[·\s]/)

  if (index !== -1) {
    return {
      surname: trimmed.slice(0, index),
      givenName: trimmed.slice(index + 1),
    }
  }

  if (/^[一-龥]/.test(trimmed)) {
    return { surname: trimmed[0], givenName: trimmed.slice(1) }
  }

  return { surname: trimmed, givenName: '' }
}
```

「王小明」でテストすると結果はまったく正しく、問題はなさそうに見えました。

## 問題は、ルールがいつまでも書き終わらないこと

氏名は、いくつかのルールで記述できるような形式ではありません：

| 入力 | 分割結果 | 問題 |
|---|---|---|
| 歐陽小明 | 歐 / 陽小明 | 複姓が分割される |
| 范姜小明 | 范 / 姜小明 | 複姓が分割される |
| 張李小明 | 張 / 李小明 | 二重姓かどうか判断できない |
| 瓦旦·達路 | 瓦旦 / 達路 | 「姓が先」とは限らない |
| John Smith | John / Smith | 英語は名が先 |
| Mary Ann Smith | Mary / Ann Smith | ミドルネームをどう扱うか |

もちろん、複姓の一覧を用意するなどしてルールを足し続けることはできます。しかし「張李」のようなケースは、文字列だけ見てもそもそも判断できません。プログラムは推測しているだけで、推測を外すのはユーザーの名前なのです。

## 最終的な修正：チームで話し合い、分割しないことに

もともとの方針は、氏名を分割して保存することでした。その後チーム内で話し合い、データベースのフィールドと照らし合わせたところ、分割する必要はないとわかりました。バックエンドは姓と名を受け取ったあと、そのままつなげて 1 つの氏名として保存していたのです。フロントエンドが苦労して分割し、バックエンドがまたつなぎ直す。分割には何の価値もありませんでした。

そこで会員登録では、ユーザーが入力したものをそのまま保存するようにしました：

```js
// 変更前
const { surname, givenName } = splitName(form.name)

// 変更後
const payload = {
  last_name: form.name,
  first_name: '',
}
```

この変更で 40 行以上を削除し、残ったのは 2 行だけです。データベースのフィールドは変えていないので、氏名全体を `last_name` に入れ、`first_name` は空にしています。

いちばんきれいなデータ構造とは言えませんが、どこが姓なのかをシステムが推測する必要はなくなり、原住民族の名前も欠けることなく保存できます。

## 分割が必要になるのはいつか

データには氏名全体を保存し、本当に分ける必要があるときだけ分割します。たとえば「王様、こんにちは」と表示したいときは、使うその場で、調整したルールに沿って自動的に分割します：

- 中点 `·` か空白があれば、最初の記号で区切る。
- 記号のない漢字の氏名は、最初の 1 文字を姓とする。
- 判断できない場合は、氏名全体を表示する。

以前との最大の違いは、分割結果を表示にだけ使い、データベースには書き戻さないことです。ルールが推測を外しても氏名全体は残っているので、あとでルールを調整すれば直せ、誤って分割されたデータが残ることはありません。

姓と名が重要な用途に関わる場合、たとえば身分証明書のデータと照合するような場合は、ルールで判断するのは適切ではありません。ユーザー自身に分けて入力してもらうべきです。

## 今回学んだこと

- テストデータがすべて通っても、ルールが正しいとは限らない。私は「王小明」しか思いついていなかった。
- 人名や住所のような現実世界のデータに出会ったら、まず自分の前提を疑う。
- ルールに例外を足し続けなければならないときは、まずそのコードがそもそも存在すべきなのかを問う。
- 手を動かす前に、データが実際にどう使われているかをチームと確認する。話し合ってみると、そこまでやらなくてよいとわかることが多い。
- コードを削除するのも修正の一つで、しかも多くの場合いちばん良い修正だ。
