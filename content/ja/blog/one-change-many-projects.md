仕事で保守しているフロントエンドは 1 つではなく複数あります。Vue 2 + Vuex のプロジェクト、Vue 3 + Pinia のプロジェクト、さらに PC 版とモバイル版が分かれたシステムもあります。どれも同じ業務を支えているので、ひとつの要件を何度も実装することがよくあります。

これは授業では学べないことでした。この記事では、実際に遭遇した状況をまとめます。

## 同じ要件を何度も実装する

実際の例をいくつか挙げます：

- 会員登録の氏名欄の調整：PC 版とモバイル版の両方を修正。
- ログイン後に元のページへ戻る：2 つのバージョンでそれぞれ実装。
- 画像ファイル名を中国語から英語へ：すべてのプロジェクトで対応。
- アクセシビリティの修正：複数のプロジェクトで基準を満たす必要がある。

これらの修正は考え方は同じでも、実装をそのままコピーできるとは限りません：

| 違い | Vue 2 プロジェクト | Vue 3 プロジェクト |
|---|---|---|
| 状態管理 | Vuex | Pinia |
| UI コンポーネントライブラリ | Vuetify 2 | Vuetify 3 |
| ルーター | Vue Router 3 | Vue Router 4 |

たとえば 404 のルートは、Vue Router 3 では `path: '*'`、Vue Router 4 では `/:pathMatch(.*)*` と書きます。考え方は同じでも書き方が違い、テストももう一度必要です。

## 最大のリスクは直し漏れ

修正の回数が増えても、時間のコストはまだ大きな問題ではありません。本当に困るのは漏れです。

私自身も経験があります。会員登録ページの氏名を分割するロジックを削除し、テストも問題なかったのに、あとからログインページの情報補完フォームにも同じロジックがあることに気づきました。しかも両方のプロジェクトでそうでした。

理由は単純で、同じロジックが同じプロジェクト内に 2 つあり、さらにプロジェクトごとにも存在していたからです。チケットには「会員登録」としか書かれていなかったので、会員登録だけを直してしまいました。

## 今のやり方

### 手を動かす前に検索する

修正する前に、すべてのプロジェクトで同じ関数やキーワードを検索し、影響範囲を確認します：

```bash
grep -rn "splitName" src
```

目の前のファイルだけを直すのが、いちばん漏れやすいやり方です。

### Notion でプロジェクトの機能一覧を作る

直し漏れが起きてから、Notion で各プロジェクトの機能を一覧にするようにしました。たとえば会員登録、ログイン、情報補完、会員情報などです。

要件が来たらまず一覧と照らし合わせてどの機能に影響するかを確認し、テストのときも一覧に沿って一つずつ確認します。こうすれば氏名のような変更も会員登録ページだけをテストして終わることはなく、ログインページの情報補完フォームもテスト範囲に入ります。

一覧は機能の追加に合わせて更新してこそ役に立ちます。機能を追加するたびについでに書き足しておけば、記憶に頼らないテスト範囲になります。

### 一度に終わらせる

同じ要件は、できるだけ同じ日にすべてのプロジェクトで対応します。間が空きすぎると当時の文脈を忘れ、バージョン間の不一致も起きやすくなります。

## 共通モジュールに切り出すべきとき

重複を見ると、まず共通パッケージに切り出したくなります。でも今はすぐにはそうしません。

**切り出すのに向いているもの**：

- フレームワークに依存しない純粋なロジック（日付のフォーマット、データの検証など）。
- 本当にまったく同じで、いつも一緒に変わるルール。
- 日付ピッカーのキーボード操作のように、同じプロジェクト内の複数ページで共有するロジックは、まず mixin や composable に切り出せます。

**すぐには切り出さないほうがよいもの**：

- UI コンポーネントライブラリに依存した画面。Vuetify 2 と 3 は大きく異なります。
- 今は似ているだけで、それぞれの要件が別の方向に進んでいくもの。

共通モジュールにもコストがあります。バージョン管理やリリースを扱う必要があり、1 か所の変更がすべてのプロジェクトに影響しかねません。Vue 2 と Vue 3 でコンポーネントを共有するのは、なおさら簡単ではありません。

私の判断基準は、まずプロジェクト内で切り出し、それが安定していて、本当に複数の場所で一緒に変わることを確認してから、プロジェクト間での共有を検討する、というものです。

## 今回学んだこと

- 複数のプロジェクトを保守するときは、「どう直すか」より「どこを直すかを知る」ほうに時間がかかる。
- 検索はもっとも安上がりな防御策。
- 重複したコードをすぐに消す必要はない。間違った抽象化は重複よりも保守が難しい。
- チケットに書かれた範囲が、実際に影響する範囲と一致するとは限らない。
