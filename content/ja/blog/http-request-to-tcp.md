ターミナルで cURL を実行すると、ふつうはリクエストと、サーバーが返した結果だけが見えます。

```bash
curl https://api.example.com/users
```

しかしこのリクエストが実際に行われるとき、コンピューターからサーバーへ直接届くほど単純ではありません。

HTTP リクエストが送られる前に、システムはすでにドメインの名前解決、ネットワーク接続の確立、そして HTTPS に必要なセキュリティのネゴシエーションを済ませているかもしれません。

これらのステップは、それぞれ別のネットワークプロトコルが担当しています。

このノートでは 1 回の API 呼び出しを出発点に、DNS、TCP、TLS、HTTP の関係を分解し、リクエストが失敗したときにどの段階で問題が起きたかをどう判断すればよいかを理解します。

## 1. 1 回の API 呼び出しは、実際にどんなステップを通るのか

まず、この HTTPS リクエストを例にします：

```bash
curl https://api.example.com/users
```

一般的な HTTP/1.1 や HTTP/2 の場合、流れはまず次のように理解できます：

```text
Client
  |
  v
DNS 問い合わせ
  |
  v
サーバーの IP を取得
  |
  v
TCP 3 ウェイハンドシェイク
  |
  v
TLS ハンドシェイク
  |
  v
HTTP Request
  |
  v
サーバーがリクエストを処理
  |
  v
HTTP Response
  |
  v
クライアントがデータを受け取る
```

段階ごとに担当が異なります：

- DNS：ドメイン名を IP アドレスに解決する。
- TCP：信頼できるデータ転送のための接続を確立する。
- TLS：暗号化された通信路を確立し、サーバーの身元を検証する。
- HTTP：リクエストとレスポンスの形式と意味を定義する。

ただし、これは流れを理解するための簡略化したモデルです。実際には DNS はキャッシュされることがあり、TCP 接続も再利用されることがあるので、API を呼び出すたびに最初から始まるとは限りません。

## 2. DNS：まずサーバーの場所を見つける

次のように入力したとき：

```bash
https://api.example.com/users
```

コンピューターは `api.example.com` をそのまま低レベルのネットワーク接続に使うわけではなく、対応する IP アドレスを取得する必要があります。

それが DNS（Domain Name System）の仕事です。

```text
api.example.com
       |
       v
   DNS 問い合わせ
       |
       v
  203.0.113.42
```

DNS は読みやすいドメイン名を IP アドレスに解決し、クライアントがどこに接続すればよいかを知らせます。

ただし、注意すべき点がひとつあります：

**DNS があるからといって、リクエストのたびに問い合わせ直すわけではありません。**

OS、ブラウザ、DNS リゾルバーはいずれも解決結果を保存していることがあり、キャッシュが有効な間は以前取得した IP をそのまま使います。

### DNS の解決に失敗するとどうなるか

ドメインを解決できないと、リクエストは次のようなエラーになることがあります：

- `Could not resolve host`
- `Temporary failure in name resolution`
- `DNS_PROBE_FINISHED_NXDOMAIN`

このとき、問題はたいていまだ TCP 接続の段階に入っていません。

まず次のコマンドで：

```bash
nslookup api.example.com
```

または：

```bash
dig api.example.com
```

ドメインが正常に解決できるかを確認できます。

## 3. TCP：3 ウェイハンドシェイクで接続を確立する

サーバーの IP を取得しても、データを転送するには、クライアントはさらに接続を確立する必要があります。

HTTP/1.1 と HTTP/2 over TCP の場合、この仕事は TCP（Transmission Control Protocol）が担当します。

TCP は 3 ウェイハンドシェイク（Three-way Handshake）で接続を確立します：

```text
Client                  Server
  |                        |
  |-------- SYN ---------->|
  |                        |
  |<----- SYN + ACK -------|
  |                        |
  |-------- ACK ---------->|
  |                        |
  |     Connection Ready   |
```

3 つのステップはそれぞれ次の意味です：

1. SYN：クライアントが接続したいことを伝える。
2. SYN-ACK：サーバーがリクエストを受け取ったことを確認し、接続情報を返す。
3. ACK：クライアントが応答を受け取ったことを確認する。

これで、双方の間に TCP 接続が確立されます。

### なぜ TCP が重要なのか

TCP はデータを送り出すだけでなく、信頼できる転送の仕組みも提供します。たとえば：

- データが正しく受信されたかを確認する。
- 失われたデータを再送する。
- データが正しい順番で届くようにする。
- フロー制御と輻輳制御で転送を調整する。

そのため HTTP は TCP を使うことで、パケットの損失や並べ替えといった低レベルの問題を自分で扱わずに済みます。

TCP 接続が確立できない場合は、次のようなエラーが出ることがあります：

- `Connection refused`
- `Connection timed out`
- `No route to host`

こうした問題は、サーバーが指定のポートで待ち受けているか、ネットワークの経路、ファイアウォール、サービスの状態などに関係している可能性があります。

## 4. TLS：HTTPS はどうやって安全な接続を確立するのか

`https://` を使う場合は、HTTP のデータを送る前に、TLS（Transport Layer Security）による安全な接続も確立する必要があります。

TLS が主に担当するのは次のことです：

- 身元の検証：証明書でサーバーの身元を検証する。
- データの暗号化：通信内容が第三者に直接読まれないようにする。
- 完全性の保護：転送中にデータが改ざんされるリスクを下げる。

TLS 1.3 のハンドシェイクを簡略化して示します：

```text
Client                  Server
  |                        |
  |----- ClientHello ----->|
  |                        |
  |<---- ServerHello ------|
  |<---- Certificate ------|
  |<---- Finished ---------|
  |                        |
  |----- Finished -------->|
  |                        |
  |   Secure Connection    |
```

実際にやり取りされるメッセージは TLS のバージョンやネゴシエーションの内容によって異なりますが、核となる目的は、以降の通信で使う暗号鍵を双方で取り決め、必要な身元の検証を済ませることです。

### TLS が失敗するとどうなるか

たとえば次のような場合です：

- 証明書の期限が切れている。
- 証明書がリクエストしたドメインと一致しない。
- 証明書チェーンを検証できない。
- TLS のバージョンや暗号スイートに互換性がない。
- プロキシやネットワーク機器がハンドシェイクを妨げている。

これらの状況では TLS ハンドシェイクが失敗することがあります。

このとき、HTTP リクエストはたいていまだ実際には送られていません。

つまり、HTTPS の接続が TLS の段階で失敗している場合、問題は API そのものとは限らず、証明書や接続の設定にある可能性があります。

## 5. HTTP：いよいよリクエストを送る

接続が確立してはじめて、HTTP がアプリケーション層のデータを送り始めます。

たとえば：

```bash
curl -X POST https://api.example.com/login \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"123456"}'
```

このリクエストにはいくつかの重要な部分があります：

| 項目 | 内容 |
| --- | --- |
| Method | POST |
| Path | /login |
| Header | Content-Type: application/json |
| Body | JSON 形式のログインデータ |

HTTP はこれらのデータの形式と意味を定義し、クライアントとサーバーが互いのリクエストとレスポンスを理解できるようにします。

たとえば：

- GET：リソースを取得する。
- POST：データを送信する、またはリソースの作成などの操作を行う。
- PUT：リソースを置き換える。
- PATCH：リソースを部分的に更新する。
- DELETE：リソースを削除する。

これが、cURL を学んでいたときに Method、Header、Body といったパラメーターを何度も目にした理由です。

これらはまさに HTTP リクエストの重要な構成要素なのです。

## 6. サーバーはリクエストを受け取ったあと何をするのか

HTTP リクエストがサーバーに届いたら、そこからはバックエンドのアプリケーションの仕事です。

ログイン API を例にすると、次のような流れになるかもしれません：

```text
HTTP Request
     |
     v
Web Server / Reverse Proxy
     |
     v
Backend Application
     |
     v
ログインデータを検証
     |
     v
データベースを検索
     |
     v
Token を生成
     |
     v
HTTP Response
```

実際の構成には、Nginx、API Gateway、ロードバランサー、アプリケーションサーバー、そのほかの内部サービスが含まれることがあります。

バックエンドはリクエストを受け取ると、通常は次のことを行います：

1. HTTP の Header と Body を解析する。
2. Token、Session、そのほかの認証情報を検証する。
3. 対応する業務ロジックを実行する。
4. 必要に応じてデータベースやほかのサービスにアクセスする。
5. HTTP レスポンスを組み立てて返す。

つまり HTTP リクエストはバックエンドのシステムへの入り口にすぎず、実際のデータ処理と業務ロジックはやはりサーバー側が担当しています。

## 7. HTTP レスポンス：サーバーはどう結果を返すのか

サーバーは処理が終わると、結果をクライアントに返します。

たとえば：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "token": "abc123",
  "user": {
    "id": 1,
    "name": "Elio"
  }
}
```

レスポンスは主に 3 つの部分に分けられます：

- Status Code：リクエストの処理結果を表す。
- Response Header：レスポンスに関する情報を記述する。
- Response Body：実際に返されるデータ。

よく使われるステータスコードは次のとおりです：

| Status Code | 意味 |
| --- | --- |
| 200 | リクエスト成功 |
| 201 | リソースの作成に成功 |
| 204 | リクエスト成功、ただしレスポンスの内容なし |
| 400 | リクエストの形式や内容に問題がある |
| 401 | 認証されていない |
| 403 | その操作を行う権限がない |
| 404 | 指定したリソースが見つからない |
| 500 | サーバー内部のエラー |

クライアントはレスポンスを受け取ってはじめてデータを解析し、フロントエンドのアプリケーションに渡します。

## 8. 実践的なデバッグ：エラーからどの層の問題かを判断する

流れ全体を理解して最も役に立つのは、実はデバッグです。

以前は API が失敗すると、まず URL、Method、パラメーターを確認するだけだったかもしれません。

でも今は、まずこう判断できます。リクエストはそもそも HTTP の段階まで到達したのか？

| 段階 | よくある問題 | まず確認すること |
| --- | --- | --- |
| DNS | ドメインが見つからない | `nslookup`、`dig` |
| TCP | 接続拒否やタイムアウト | IP、ポート、ファイアウォール |
| TLS | 証明書やハンドシェイクの失敗 | 証明書、TLS の設定 |
| HTTP | 400、401、403、404 | Method、Header、Body |
| Server | 500、サービスの異常 | バックエンドのログ、データベース、サービスの状態 |

### cURL で接続の詳細を見る

リクエストで実際に何が起きているかを知りたいときは、次のようにします：

```bash
curl -v https://api.example.com/users
```

`-v`（verbose）を付けると、たとえば次のような詳しい接続情報が表示されます：

- DNS の解決後に使われた IP。
- TCP 接続の確立の過程。
- TLS のハンドシェイクと証明書の情報。
- 送信したリクエストヘッダー。
- 受信したレスポンスヘッダー。

HTTP のステータスコードだけを確認したい場合は、次のようにもできます：

```bash
curl -sS -o /dev/null -w "%{http_code}\n" \
  https://api.example.com/users
```

これで HTTP のステータスコードを直接取得できます。

注意したいのは、DNS、TCP、TLS の段階で失敗している場合は、有効な HTTP ステータスコードが得られないかもしれないことです。

また、`curl -v` の出力には Cookie や Authorization などの機密情報が含まれることがあるので、デバッグのログを共有する前に必ず伏せてください。

## 9. さらに理解を深める：HTTP/1.1、HTTP/2、HTTP/3 の違い

ここまで紹介した TCP の 3 ウェイハンドシェイクと TLS の流れは、主に一般的な HTTP/1.1、HTTP/2 over TCP を例にしたものです。

しかし HTTP の転送方法は 1 種類だけではありません。

現在よく使われるバージョンは、簡単に次のように区別できます：

| プロトコル | 転送の基盤 | 主な特徴 |
| --- | --- | --- |
| HTTP/1.1 | TCP | 持続的接続に対応するが、複数のリクエストの転送効率には限りがある |
| HTTP/2 | TCP | 多重化に対応し、複数のリクエストの処理効率を改善 |
| HTTP/3 | QUIC（UDP） | 転送とセキュリティの仕組みを統合し、接続の確立と転送の性能を改善 |

なかでも注目すべきは HTTP/3 です。

HTTP/3 は TCP を使わず、QUIC を転送の基盤にしています。

QUIC は UDP の上に構築され、TLS 1.3 のセキュリティの仕組みを統合し、信頼できる転送、多重化、接続管理などの機能を提供します。

そのため、すべての HTTP リクエストが必ず TCP の 3 ウェイハンドシェイクを通るわけではありません。

これは、ネットワークプロトコルを理解するときに、HTTP、TCP、HTTPS を同じ層の概念として扱ってはいけない理由も示しています。

## 10. 今回学んだこと

cURL で API をテストするところから始めて、DNS、TCP、TLS、HTTP を理解するところまで進んでみて、本当に身につけるべきなのはひとつのコマンドではなく、リクエストのライフサイクル全体なのだと気づきました。

今回まとめてみて、重要だと思った考え方がいくつかあります：

- DNS はドメインを解決するが、リクエストのたびに問い合わせ直すわけではない。
- TCP は信頼できる転送を提供するが、HTTP/3 が使うのは TCP ではなく QUIC。
- HTTPS は単に HTTP を暗号化したものではなく、TLS によって安全な通信を確立している。
- HTTP はリクエストとレスポンスの形式と意味を定義する。
- API でエラーが起きたら、まず問題がどのネットワーク層・アプリケーション層で起きているかを判断する。

**API を本当に理解するとは、リクエストの送り方を知ることだけではなく、リクエストがどう接続を確立し、どう転送されるのか、そして失敗したときにどこから調べ始めればよいのかを知ることです。**

これが、cURL からネットワークプロトコルへと学びを広げて得た、いちばん大きな収穫です。
