既存のシステムを引き継いだとき、いちばん難しいのは技術そのものではなく、「ここを変えるとどこに影響するのかわからない」ことです。

特になじみのないコードで、問題を見つけてすぐに直そうとすると、表面だけを直して本当の解決にならないことがよくあります。

あとになって気づいたのは、こうした状況では、どの行に問題があるかを急いで探すよりも、まず明確なデバッグの流れを作ることのほうが大切だということです。つまり**再現、特定、原因の究明、修正、再発防止**です。

この記事では、既存システムを保守するときに使っている考え方をまとめます。

## 1. 再現：まず問題を安定して起こす

安定して再現できない問題は、直したとしても直ったことを証明できません。

そのため最初のステップはコードを変えることではなく、問題が起きる条件を確認することです：

- どのページで、どんな操作の順番で、どんなデータのときか。
- 特定のブラウザ、画面サイズ、ログインしている権限のときだけ起きるのか。
- 最小再現例（Minimal Reproduction）まで絞り込めるか。関係のないコードを取り除いても問題が残るなら、範囲を正しく絞り込めている。

問題が特定の条件でしか起きないなら、その条件を記録しておきます。テストのたびに違う状況を使ってしまい、最終的に変更が本当に効いたのか判断できなくなるのを防ぐためです。

## 2. 特定：二分法で範囲を絞る

問題を再現できるとわかったら、次は問題が起きている場所を探します。

私はたいていブラウザの DevTools から始めます：

- **Console**：まずエラーや警告がないかを見る。方向を直接示してくれることが多い。
- **Network**：リクエストが送られたか、ステータスコード、返ってきたデータが期待どおりかを確認する。
- **Elements**：実際に適用されている CSS と、対象のルールが上書きされていないかを見る。
- **Sources**：怪しい場所にブレークポイントを置くか、Event Listener Breakpoints で特定のイベントが起きたときに一時停止する。

最初からプロジェクト全体のコードを読み通そうとしないことです。

まず問題がフロントエンドの操作で起きているのか、API リクエストなのか、データが返ってきたあとなのかを確認し、それから少しずつ範囲を絞ります。

## 3. 原因の究明：推測ではなく仮説を検証する

UI の挙動の問題によくある原因は、まず一覧と照らし合わせて確認できます：

| 現象 | よくある原因 | 検証方法 |
| --- | --- | --- |
| ポップアップや外側の UI がすぐ閉じる、または閉じない | イベントのバブリングや順番。クリック後に上位の要素が横取りしている | capture フェーズでイベントの経路を記録する |
| コンポーネントの値が更新されない | リアクティブ性の喪失（分割代入、非リアクティブなオブジェクト） | DevTools でその値がまだリアクティブかを確認する |
| スタイルを変えても効かない | セレクターの詳細度が低い、または同じ重みのスタイルに上書きされている | Elements パネルで上書きされているルールを確認する |
| オーバーレイが隠れる | stacking context によって `z-index` が効かない | 祖先要素に `transform`、`opacity` などがないかを確認する |
| ときどき起きるエラー | 非同期のタイミングやリクエストの競合 | タイムスタンプ付きのログを入れて順番を比べる |

たとえば、どの層がクリックを横取りしているかを確認したいなら、capture フェーズでイベントの経路を観察できます：

```js
document.addEventListener('click', (e) => {
  console.log('capture:', e.target, e.composedPath())
}, true)
```

こうしてイベントが実際にどの要素を通っているかを確認してから、イベント処理を変える必要があるかを判断します。

大切なのは、ある現象を見てすぐ見慣れた解決策を当てはめることではなく、まず仮説を立て、ツールで検証することです。

## 4. 修正：範囲は最小限に、影響範囲を評価する

原因が見つかっても、すぐに大きく書き換えてよいわけではありません。

変更する前に、3 つの問いに答えます：

1. このコードはほかにどこで使われているか。（全体を検索し、参照を確認する）
2. 変更によって既存のどの挙動が変わるか。
3. もっと小さな変更方法はないか。たとえば呼び出し側すべてに手を入れるのではなく、コンポーネント自体を直す。

既存システムには十分なテストがないことが多いので、変更後は報告された 1 つの状況を確認するだけでなく、「影響を受けるフロー」を手動で通すことがいっそう重要になります。

たとえば共通コンポーネントのイベントの挙動を直すなら、今のページが正常かを確認するだけでは足りず、そのコンポーネントを使っているほかのページに影響が出ていないかも確認します。

## 5. 再発防止：同じ問題を二度と起こさない

問題を直したら、もう一歩考えられます。次はもっと早く気づけるようにできないか、ということです。

- 元の問題を再現できるテストを追加する。テスト環境がなければ、少なくとも再現手順を PR の説明に書いておく。
- ツールで防げるものはルールにする。たとえば ESLint のルールや、コンポーネントの props の制約。
- 関連する情報をコードのコメントやドキュメントに残す。書くのは「何をしたか」ではなく「なぜそうしたか」。

これらを一度にすべてやる必要はありませんが、同じ問題が再び起きる可能性を少しずつ下げられます。

## 今回学んだこと

既存システムを保守していると、問題を見つけたらすぐに直したくなりがちです。しかし実際には、問題が起きる条件や元のプログラムの実行の流れを先に把握していないと、表面だけを直してしまったり、もともと正常だったほかの機能に影響を与えたりしやすくなります。

今回まとめてみて、デバッグとはエラーの起きている場所を見つけることだけではなく、なぜそれが起きるのか、そして変更が別の影響をもたらさないかを理解することのほうが大切だと気づきました。

特になじみのないコードに向き合うときは、まず問題の範囲を絞り、原因を確かめてから直し方を決めるほうが、急いで手を動かすよりたいてい効率的です。

私にとって既存システムの保守は、プログラムの設計を理解する過程でもあります。問題を元に戻すだけでなく、同じ問題を二度と起こさない方法がないかも考えたいと思っています。
