以前ウェブページを開発していたときは、まず機能が正常に動くか、画面が期待どおりかを確認するのが普通でした。

しかし関わるプロジェクトが増えるにつれ、機能が正常に動くからといって、そのページにほかの問題がないとは限らないと気づくようになりました。

コードを変えたことで既存の機能に影響が出ていないか、ユーザーがキーボードで操作を完了できるか、ページの読み込みは十分に速いか。どれも開発中に見落としやすいのに、実際の使い心地に影響する細かな点です。

この記事では、フロントエンド開発でよく問題になる 3 つの品質の側面、つまりテスト戦略、アクセシビリティ、パフォーマンス指標をまとめます。

## 1. テスト戦略：実装ではなく振る舞いをテストする

フロントエンドのテストは、一般的に 3 つの層に分けられます：

| 層 | ツールの例 | 検証する内容 | コスト |
| --- | --- | --- | --- |
| 単体テスト | Vitest | 関数、ユーティリティ、独立したロジック | 低 |
| コンポーネントテスト | Vue Test Utils | ユーザーに見えるコンポーネントの結果 | 中 |
| E2E テスト | Playwright | ログインや注文などの一連のフロー | 高 |

コンポーネントテストの原則は「ユーザーと同じように操作し、ユーザーに見える結果を確認する」ことで、コンポーネント内部の変数名を確認することではありません。

たとえば Vue Test Utils と Vitest を使うと：

```ts
import { mount } from '@vue/test-utils'
import { describe, expect, it } from 'vitest'
import Counter from './Counter.vue'

describe('Counter', () => {
  it('ボタンをクリックすると、表示される数字が 1 増える', async () => {
    const wrapper = mount(Counter)

    await wrapper.get('button').trigger('click')

    expect(wrapper.text()).toContain('1')
  })
})
```

このテストが気にしているのは、ユーザーがボタンをクリックしたあとに画面が正しく更新されるかであって、コンポーネントが内部でどの変数を使っているかではありません。

### モックの境界

モックは、できるだけシステムの境界に近い場所に置くのが理想です。

たとえば、自分の内部の関数やコンポーネントの状態を直接モックするのではなく、MSW で API のレスポンスをモックします。

内部のコードまですべてモックしてしまうと、テストはアプリケーションの振る舞いではなく、モックそのものを検証しているだけになりかねません。

## 2. アクセシビリティ：キーボードから始める

アクセシビリティは見た目のデザインだけの問題ではなく、ユーザーがページをスムーズに操作できるかどうかにも関わります。

いちばん始めやすい確認方法は、まずキーボードだけでページを操作してみることです：

- `Tab` で、すべての操作可能な要素を自然な順番でたどれるか。
- 今どこにフォーカスがあるかがはっきりしているか。（`outline` を消さない、または `:focus-visible` で独自のスタイルを付ける）
- ダイアログを開いたとき、フォーカスがダイアログの中に移るか。`Esc` で閉じられるか。閉じたあと、フォーカスが元のボタンに戻るか。
- すべてを `<div>` にクリックイベントを付けて作るのではなく、`<button>`、`<a>`、`<label>` などのセマンティックな要素を使う。

たとえば：

```css
:focus-visible {
  outline: 2px solid #1d4ed8;
  outline-offset: 2px;
}
```

こうすると、キーボードで操作しているときにフォーカスのある要素がはっきりわかるようになります。

自動化ツール（axe など）でアクセシビリティの問題の一部は見つけられますが、操作の流れが妥当かどうかは判断できないので、やはり実際にキーボードを使った手動の確認が必要です。

## 3. パフォーマンス：Core Web Vitals

Google の Core Web Vitals は、現在主に次の 3 つです：

| 指標 | 測定する内容 | 良好 |
| --- | --- | --- |
| LCP（Largest Contentful Paint） | 最大のコンテンツが描画されるまでの時間 | 2.5 秒以下 |
| INP（Interaction to Next Paint） | 操作後に画面が応答するまでの時間 | 200 ミリ秒以下 |
| CLS（Cumulative Layout Shift） | レイアウトのずれの大きさ | 0.1 以下 |

これらはそれぞれ、ページの読み込み、操作への応答、画面の安定性を表しています。

### よくある改善の方向

- **LCP**：最大の画像には適切な形式とサイズを使い、主要なコンテンツの読み込み優先度を上げ（たとえば `fetchpriority="high"`）、レンダリングを妨げるリソースを減らす。
- **INP**：長時間実行される JavaScript を小さく分割し、メインスレッドをふさがないようにする。
- **CLS**：画像や埋め込みコンテンツにあらかじめ `width`、`height` または `aspect-ratio` を指定し、ブラウザに領域を確保させる。

たとえば：

```html
<img
  src="/cover.webp"
  width="1600"
  height="728"
  alt="プロジェクトのカバー"
  fetchpriority="high"
/>
```

画像のサイズをあらかじめ指定しておけば、ブラウザは画像が読み込まれる前に領域を確保でき、読み込み後にレイアウトがずれる可能性を下げられます。

## 4. 大規模プロジェクトの保守の考え方

プロジェクトの規模が大きくなると、品質管理を開発者自身のチェックだけに頼ることはできなくなります。

次のような方向から始められると思います：

- **エラーを早く表に出す**：TypeScript、ESLint、型付きの API レスポンスで、編集時やコミット時にエラーを見つける。
- **小さく変更し、元に戻せるようにする**：変更の範囲が小さいほどレビューしやすく、ロールバックもしやすい。
- **ルールをツールにする**：CI で自動チェックできるもの（フォーマット、型、テスト）は、人の記憶に頼らない。
- **「なぜ」を残す**：コメントやドキュメントに判断の理由を記録しておけば、引き継いだ人がいつ変えてよいかを判断できる。

これらは最初から完全なエンジニアリングのプロセスを導入する必要はなく、プロジェクトの規模やチームのニーズに合わせて少しずつ整えていけます。

## 今回学んだこと

以前ウェブページを開発していたときは、まず機能が正常に動くか、画面が期待どおりかを確認するのが普通でした。しかし関わるプロジェクトが増えるにつれ、機能が正常に動くからといって、そのページにほかの問題がないとは限らないと気づくようになりました。

ユーザーがキーボードで操作を完了できるか、コードを変えたことで既存の機能に影響が出ていないか、ページの読み込みは十分に速いか。どれも開発中に見落としやすいのに、実際の使い心地に影響する細かな点です。

テスト、アクセシビリティ、パフォーマンスの最適化は別々のことに見えますが、実はどれも同じ問題を扱っています。完成した機能を「使える」だけでなく、品質を保ち続けられるものにするにはどうすればよいか、という問題です。

エンジニアリングの品質はプロジェクトが完成してから確認するものではなく、開発や修正の過程で検証を考慮に入れるべきものだということも、少しずつ理解できるようになりました。
