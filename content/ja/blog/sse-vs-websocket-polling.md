LINE 公式アカウント管理プラットフォームの管理画面には、通知のベルがあります。データが編集されたとき、予約が審査されたとき、新しいユーザーが友だち追加したときに、店舗オーナーがページを更新しなくてもすぐ気づけるようにするためです。

HTTP はもともと「ブラウザが尋ね、サーバーが答える」仕組みなので、サーバーから先に話しかけることはできません。リアルタイム通知を実現するには、サーバーのメッセージをブラウザに届ける方法を選ぶ必要があります。この記事では、よくある方法と、私が SSE を選んだ理由をまとめます。

## 4 つの方法

### Short Polling：一定間隔で尋ねる

フロントエンドが `setInterval` で数秒ごとに API を呼び、「新しい通知はありますか？」と尋ねます。

```js
setInterval(async () => {
  const { data } = await api.get('/notifications')
  notifications.value = data.result
}, 5000)
```

いちばん簡単で、どんな環境でも使えます。欠点は、ほとんどのリクエストが空振りになることです。間隔を長くするとリアルタイム性が下がり、短くすると通信量とサーバーの負荷が増えます。

### Long Polling：尋ねて、待つ

フロントエンドがリクエストを送ると、サーバーは**すぐには答えず**、新しいデータができるまで待ってから返します。フロントエンドは応答を受け取るとすぐ次のリクエストを送ります。Short Polling よりリアルタイムですが、通知のたびにリクエストを作り直す必要があり、サーバーは待機中の接続をたくさん抱えることになり、タイムアウトや再接続も自分で処理しなければなりません。

**両者の違いは、いつ応答するかを誰が決めるかです。** Short Polling は、フロントエンドが決まったリズムで尋ね、サーバーは新しいデータの有無にかかわらずすぐ返します。Long Polling は、サーバーがデータができる（またはタイムアウトする）まで、リクエストを保留します。つまり Long Polling はポーリングをやめたわけではなく、「どのくらいの間隔で尋ねるか」を、サーバー側のイベントやタイムアウトで決めるようにしたものです。

![Short Polling と Long Polling のリクエストの流れの比較：Short Polling ではフロントエンドが一定間隔でリクエストを送り、サーバーはすぐ応答するため空の応答が多くなります。Long Polling ではサーバーがリクエストを保留し、新しいデータかタイムアウトで応答し、フロントエンドは応答を受け取るとすぐ次のリクエストを送ります。](/images/blog/short-vs-long-polling.svg)

### SSE（Server-Sent Events）：一方向の長い接続

ブラウザは普通の HTTP リクエストを 1 つ送り、サーバーは**応答を終わらせず**、メッセージを少しずつ書き込んでいきます。ブラウザには受信用の `EventSource` が組み込まれています。

応答は決まった形式のプレーンテキストです。

```
event: notification
data: {"title":"予約が承認されました"}

:ping
```

メッセージは空行で終わります。コロンで始まる行はブラウザが無視するコメントで、ハートビートによく使われます。

### WebSocket：双方向の接続

最初に HTTP のアップグレードリクエストを送り（応答は `101 Switching Protocols`）、その後の接続は HTTP ではなく、どちらからもいつでもデータを送れる双方向の通路になります。

```js
const ws = new WebSocket('wss://example.com/chat')
ws.onmessage = (e) => console.log(e.data)
ws.send('hello')
```

チャット、対戦ゲーム、共同編集のように、双方が頻繁にデータを送る場面では、これが正解です。

## 比較表

| | Short Polling | Long Polling | SSE | WebSocket |
|---|---|---|---|---|
| 方向 | フロントが尋ねる | フロントが尋ね、サーバーが返事を遅らせる | サーバー → フロント | 双方向 |
| プロトコル | HTTP | HTTP | HTTP | HTTP のハンドシェイク後に WebSocket へアップグレード |
| リアルタイム性 | 間隔次第 | 高い | 高い | 高い |
| 再接続 | 不要 | 自分で書く | ブラウザが自動で行う | 自分で書く |
| データ形式 | 何でも | 何でも | UTF-8 テキスト（JSON 文字列も可） | テキストまたはバイナリ |
| カスタムヘッダー | 可能 | 可能 | `EventSource` では不可 | ブラウザ API では不可 |
| サーバーの負担 | 処理するリクエストが多い | 待機中のリクエストが多い | 長い接続を保ち、データを送る必要がある | 長い接続を保ち、接続状態とメッセージも管理する |
| 向いている場面 | 低頻度・簡単 | ほかに手段がないとき | 通知、進捗、ライブボード | チャット、ゲーム、共同作業 |

比較によく出てくるものに Web Push もあります。ブラウザや OS レベルのプッシュで、ページを閉じていても届きますが、許可の取得や購読の管理が必要で、ページを開いている間のリアルタイム更新とは別の問題を扱うものです。今回は使っていません。

## SSE を選んだ理由

選ぶ前に、「データは双方向に流れる必要があるか？」と自分に問いました。

管理画面の通知は、サーバーからフロントエンドへ送るだけです。既読にするのは普通の `PATCH` リクエストで済むので、そのために双方向の通路を保つ必要はありません。そこで次のように考えました。

- **WebSocket の双方向の機能は使わない**のに、ハートビート、再接続、認証を自分で処理することになります。
- **SSE は普通の HTTP リクエスト**なので、ログインに使っている HttpOnly Cookie がそのまま送られ、既存の認証ミドルウェアをそのまま使えます。WebSocket のハンドシェイクにも Cookie は付きますが、Origin の確認やアップグレード時の認証処理を自分で用意する必要があり、その分の手間が増えます。
- **`EventSource` は切断後に自動で再接続**してくれます。
- **Polling は無駄が多い**：通知はそれほど頻繁ではなく、ほとんどのリクエストが空振りになります。Render の無料プランで動かしているので、無駄にリクエストを増やしたくありませんでした。

## 実装の様子

### バックエンド：応答を閉じずに保つ

```js
export const stream = (req, res) => {
  res.set({
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    Connection: 'keep-alive'
  })
  res.flushHeaders()

  const listener = (doc) => {
    res.write(`event: notification\ndata: ${JSON.stringify(doc)}\n\n`)
  }
  notificationBus.on(shopId, listener)

  // 間のプロキシが接続を待機中と判断して切らないよう、定期的にコメント行を送る
  const keepAlive = setInterval(() => res.write(':ping\n\n'), 30 * 1000)

  req.on('close', () => {
    clearInterval(keepAlive)
    notificationBus.off(shopId, listener)
  })
}
```

ポイントは 3 つです。ヘッダーを `text/event-stream` にすること、`res.end()` を呼ばないこと、接続が閉じたらリスナーとタイマーを片付けることです。片付けないと溜まり続けます。

通知が作られると、まず データベース に保存し、次に Node.js 標準の `EventEmitter` でイベントを発行します。接続中の SSE がそれを受け取ります。先に保存するのは、ちょうどそのとき接続が切れているかもしれず、通知が「プッシュした一瞬」にしか存在しない状態にしてはいけないからです。

### フロントエンド：EventSource

```js
const url = `${import.meta.env.VITE_API}/notifications/stream?shopId=${shopId}`
eventSource = new EventSource(url, { withCredentials: true })

eventSource.addEventListener('notification', (event) => {
  const notification = JSON.parse(event.data)
  if (notifications.value.some(n => n._id === notification._id)) return
  notifications.value.unshift(notification)
  unreadCount.value++
})
```

## 当たった制限

**`EventSource` はカスタムヘッダーを付けられません。** 通常の API リクエストでは「どの店舗を見るか」をヘッダーに入れられますが、`EventSource` ではヘッダーを足せません。そのため、ストリームのエンドポイントだけは URL のパラメーターで受け取る形にしました。`withCredentials: true` で Cookie も一緒に送られます。

**店舗を切り替えたら再接続します。** オーナーは複数の店舗を管理できます。切り替えるときは、古い接続を閉じて一覧を空にし、新しい店舗に対して接続し直します。古い店舗のレスポンスが遅れて届いた場合は、新しい店舗のデータを上書きしないよう破棄します。

**重複の対策が必要です。** 同じ通知が「一覧の取得」と「SSE のプッシュ」の両方から届くことがあるので、`_id` で重複を除きます。

**今のところ、サーバーが 1 台の場合だけ対応しています。** `EventEmitter` は 1 つの Node.js プロセスのメモリ内にしかありません。サーバーが複数台になると、A のマシンで作られた通知は、B のマシンにつないでいるユーザーに届きません。その場合は Redis Pub/Sub のような仕組みに置き換える必要があります。この上限はコードにコメントで残してあります。

**再接続後に取りこぼした通知を補っていません。** `EventSource` は自動で再接続しますが、切断中に逃した通知は、ページを更新するか店舗を切り替えて一覧を取得し直したときにしか戻りません。再接続後に一覧 API をもう一度呼ぶ、または SSE の `id` フィールドと `Last-Event-ID` を使ってサーバーに再送してもらう方法がありますが、まだ実装していません。

また、HTTP/1.1 ではブラウザがドメインごとの接続数を制限しており（通常 6 本）、SSE の接続は 1 本を占有します。同じサイトのタブをたくさん開くと枠を奪い合います。HTTP/2 では 1 本の接続上で多重化され、上限もずっと高いため、この問題はほとんど目立ちません。

## どう選ぶか

1. データがサーバーからフロントエンドへ流れるだけ（通知、進捗バー、ライブボード）→ **SSE**
2. 双方が頻繁にデータを送る（チャット、ゲーム、共同作業）→ **WebSocket**
3. 更新が少ない、環境に制約がある、遅れても構わない → **Short Polling**
4. ページを閉じていても届けたい → **Web Push**

## 今回学んだこと

技術を選ぶときは、「どれが強いか」より先に「データはどちらへ流れるか」を考えるほうが役に立ちます。WebSocket は機能が多いものの、余分な能力を使わないなら、自分で維持するものが増えるだけです。

また、リアルタイムのプッシュは「ユーザーがより早く見られる」ようにするだけで、データそのものは先に保存しておく必要があります。通知をデータベースに書き込んでおけば、プッシュが失敗しても接続が切れても何も失われません。この設計でいちばん大事なのはそこだと思っています。
