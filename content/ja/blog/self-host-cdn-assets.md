会社のプロジェクトで脆弱性診断を受けたところ、レポートに中リスクの項目「クロスオリジンの設定不備」が挙がっていました。最初はバックエンドの CORS 設定だと思っていましたが、調べていくと、フロントエンドで読み込んでいるアイコンフォントに関係していることがわかりました。

## 問題は 1 行の @import

プロジェクトでは Material Design Icons を使うため、CDN からアイコンを読み込む CSS ファイルを書いていました：

```css
@import url("https://cdn.jsdelivr.net/npm/@mdi/font@latest/css/materialdesignicons.min.css");
```

この書き方は手軽でよく見かけますが、いくつかの問題があります。

## サードパーティのリソースのリスク

### 1. サイトが他人のサーバーに依存する

CDN 上の CSS やフォントは別のドメインから読み込まれます。CDN に障害が起きたり、ユーザーのネットワーク環境がそのドメインをブロックしたりすると、アイコンがすべて表示されなくなります。

ネットワーク環境が制限されている組織では特に起きやすく、しかも開発中にはまったく気づけません。

### 2. `@latest` は内容がいつでも変わることを意味する

`@latest` は固定のファイルではなく、「現時点での最新バージョン」です。つまり：

- パッケージの新しいバージョンが出ると、デプロイしていないのにサイトの内容が変わる。
- 新しいバージョンでアイコン名が変わると、コードは一切変えていないのに画面が突然壊れることがある。
- 上流に悪意のあるコードが仕込まれたら、自分のサイトもそれをそのまま読み込む。

CSS は JavaScript を直接実行できませんが、サードパーティの内容が自分の画面に影響を与えられること自体が信頼の問題です。

### 3. 完全性チェックができない

ブラウザには Subresource Integrity（SRI）があり、ファイルの内容が改ざんされていないかを確認できます：

```html
<link
  rel="stylesheet"
  href="https://cdn.example.com/lib@1.2.3/style.css"
  integrity="sha384-..."
  crossorigin="anonymous"
>
```

しかし SRI が比較するのは固定された内容のハッシュ値です。`@latest` の内容は変わるので、更新されたとたんに照合に失敗します。しかも CSS の `@import` で読み込む場合は、`integrity` を書く場所すらありません。

## 解決策：セルフホストに切り替える

修正は単純で、CSS とフォントファイルをプロジェクトに入れ、自分のサーバーから配信します。

```text
src/assets/
├── customized/
│   └── materialdesignicons.min.css
└── fonts/
    ├── materialdesignicons-webfont.woff2
    └── materialdesignicons-webfont.woff
```

エントリーファイルでローカルの CSS を読み込むように変えます：

```js
// main.js
import './assets/customized/materialdesignicons.min.css'
```

そのうえで CSS の `@font-face` のパスをローカルのフォントに向けます。これですべてのリソースが同じオリジンから配信され、バージョンも固定されます。更新するときだけ手動で差し替えます。

## その代償

セルフホストにもコストはあります：

- フォントファイルは小さくないうえ、プロジェクト側でこれらのリソースのキャッシュと配信も担う必要がある。
- バージョンは自動で更新されないので、セキュリティ修正が出ていないか自分で気にかける必要がある。
- CSS ファイルがバージョン管理に入る。このファイルだけで 2 万行以上ある。

やり直すなら、npm でバージョンを固定した `@mdi/font` をインストールします：

```js
import '@mdi/font/css/materialdesignicons.min.css'
```

フォントのパスはバンドラーが処理してくれ、バージョンは `package-lock.json` に記録されるので、ファイルを手でコピーするより保守しやすくなります。使うアイコンが少なければ、SVG に切り替えて必要な分だけバンドルする方法もあります。

モダンブラウザはすべて woff2 に対応しているので、通常は woff2 だけ残せば十分で、eot や ttf まで持っておく必要はありません。

## プロジェクトにほかにも同じ問題がないか確認する方法

```bash
# コード内の外部リソースを探す
grep -rnE "https?://" src index.html

# バージョンが固定されていない読み込みには特に注意
grep -rn "@latest" src index.html
```

DevTools の Network パネルを開いてサードパーティのドメインで絞り込み、実際にどのリソースが読み込まれているかを確認することもできます。

## 今回学んだこと

- 脆弱性診断の項目は、思っている場所にあるとは限らない。実際の出どころまで追いかける。
- 手軽な 1 行の読み込みの裏には、サードパーティへの信頼がある。公開前にそれだけの価値があるかよく考える。
- 本番環境では `@latest` を使わない。バージョンを固定してはじめて、サイトが実際に何を読み込んでいるかを把握できる。
