以前在開發網頁時，我通常會先確認功能能不能正常運作、畫面有沒有符合預期。

但隨著接觸的專案越來越多，我開始發現，功能正常不代表整個網頁就沒有其他問題。

像是修改程式後有沒有影響原本的功能、使用者能不能透過鍵盤完成操作，以及頁面載入速度是否理想，這些都是開發過程中容易忽略，卻會實際影響使用體驗的細節。

這篇整理前端開發中常見的三個品質面向：測試策略、無障礙，以及效能指標。

## 一、測試策略：測行為，不測實作

前端測試常見可以分成三層：

| 層級 | 工具範例 | 驗證什麼 | 成本 |
| --- | --- | --- | --- |
| 單元測試 | Vitest | 函式、工具函式、獨立邏輯 | 低 |
| 元件測試 | Vue Test Utils | 使用者看到的元件結果 | 中 |
| 端對端測試 | Playwright | 完整流程（登入、下單等） | 高 |

元件測試的原則是「像使用者一樣操作，檢查使用者看得到的結果」，而不是檢查元件內部的變數名稱。

例如使用 Vue Test Utils 與 Vitest：

```ts
import { mount } from '@vue/test-utils'
import { describe, expect, it } from 'vitest'
import Counter from './Counter.vue'

describe('Counter', () => {
  it('點擊按鈕後，顯示的數字加一', async () => {
    const wrapper = mount(Counter)

    await wrapper.get('button').trigger('click')

    expect(wrapper.text()).toContain('1')
  })
})
```

這個測試關心的是使用者點擊按鈕後，畫面有沒有正確更新，而不是元件內部使用了哪個變數。

### Mock 的邊界

Mock 的位置最好越接近系統邊界越好。

例如使用 MSW 模擬 API 回應，而不是直接 Mock 自己的內部函式或元件狀態。

如果把內部程式碼也全部 Mock 掉，測試可能只是在驗證 Mock 本身，而不是真正驗證應用程式的行為。

## 二、無障礙：從鍵盤開始

無障礙不只是視覺設計的問題，也關係到使用者能不能順利操作網頁。

最容易開始的檢查方式，就是先嘗試只使用鍵盤操作頁面：

- `Tab` 能依照合理順序走遍所有可互動元素嗎？
- 目前焦點的位置是否清楚？（不要移除 `outline`，或使用 `:focus-visible` 自訂樣式）
- 彈窗打開時，焦點有沒有進入彈窗？按 `Esc` 能關閉嗎？關閉後焦點有沒有回到原本按鈕？
- 用 `<button>`、`<a>`、`<label>` 等語意化元素，而不是全部用 `<div>` 綁點擊事件。

例如：

```css
:focus-visible {
  outline: 2px solid #1d4ed8;
  outline-offset: 2px;
}
```

這樣可以在鍵盤操作時，讓目前焦點的元素有明顯的視覺提示。

自動化工具（例如 axe）能抓到部分無障礙問題，但無法判斷操作流程是否合理，所以仍需要實際使用鍵盤手動檢查。

## 三、效能：Core Web Vitals

Google 的 Core Web Vitals 目前主要有三項：

| 指標 | 衡量 | 良好 |
| --- | --- | --- |
| LCP（Largest Contentful Paint） | 最大內容繪製時間 | ≤ 2.5 秒 |
| INP（Interaction to Next Paint） | 互動後的畫面回應時間 | ≤ 200 毫秒 |
| CLS（Cumulative Layout Shift） | 版面配置位移程度 | ≤ 0.1 |

這些指標分別反映頁面載入、互動回應與畫面穩定性。

### 常見的改善方向

- **LCP**：最大的圖片使用適當格式與尺寸，並提高主要內容的載入優先權，例如使用 `fetchpriority="high"`，減少阻塞渲染的資源。
- **INP**：把長時間執行的 JavaScript 拆小，避免阻塞主執行緒。
- **CLS**：圖片與嵌入內容事先指定 `width`、`height` 或 `aspect-ratio`，讓瀏覽器預先保留空間。

例如：

```html
<img
  src="/cover.webp"
  width="1600"
  height="728"
  alt="專案封面"
  fetchpriority="high"
/>
```

透過事先指定圖片尺寸，瀏覽器就能在圖片載入前預留空間，降低圖片載入後造成版面位移的機會。

## 四、大型專案的維護思維

當專案規模逐漸增加，品質管理就不能只依賴開發者自己檢查。

我認為可以從幾個方向開始：

- **讓錯誤提早出現**：TypeScript、ESLint、型別化的 API 回傳，提早讓錯誤在編輯與提交階段被發現。
- **小步修改、可回復**：每次變更範圍小，才容易 Review，也容易回退。
- **把規則寫成工具**：能由 CI 自動檢查的（格式、型別、測試），就不要靠人記憶。
- **留下「為什麼」**：註解與文件記錄決策原因，接手的人才能判斷何時可以改。

這些做法不一定要一開始就導入完整的工程化流程，可以依照專案規模與團隊需求逐步建立。

## 這次學到的事

以前在開發網頁時，通常會先確認功能能不能正常運作、畫面有沒有符合預期。但隨著接觸的專案越來越多，我開始發現，功能正常並不代表這個網頁就沒有其他問題。

像是使用者能不能透過鍵盤完成操作、修改程式後有沒有影響原本的功能，以及頁面載入速度是否理想，這些都是開發過程中容易忽略，卻會實際影響使用體驗的細節。

測試、無障礙與效能優化看起來是不同的事情，但它們其實都在處理同一個問題：如何讓完成的功能不只是能用，也能持續維持品質。

我也逐漸理解，工程品質不是等到專案完成後才開始檢查，而是應該在開發與修改的過程中，就把驗證這件事納入考量。
