工作上的 GIS 圖台原本就有快照碼功能，可以記錄特定的地圖檢視狀態，讓使用者透過代碼回到對應的圖資畫面。

在既有 GIS 圖台進行功能擴充時，我需要將原本的快照碼能力整合到新的操作情境。這篇聚焦技術判斷，省略實際業務條件與介面細節。

我主要負責前端功能開發，先研究原有程式，確認快照碼怎麼運作、API 提供哪些資料，再規劃操作介面與功能流程。

這篇記錄的是這次前端整合的過程。使用的技術包含 Vue、OpenLayers 與 REST API，重點放在既有功能與資料流程的理解。

## 先確認原本的功能怎麼運作

接到需求時，我先看既有快照碼功能的程式碼，理解它如何與圖台定位銜接。

要確認的事情包含：

- 既有快照碼功能在系統中的觸發方式與執行流程。
- 程式取得快照碼後，如何讓圖台回到對應畫面。
- 新需求能沿用哪些既有邏輯。
- 新增操作後，會經過哪些原有流程。

這些關係弄清楚後，才確認這次可以沿用原本的快照碼機制，把它接進新的操作情境，不需要重新做一套。

對我來說，這一步比較花時間的是找到功能之間的關係。單看某個函式知道它在做什麼，還不代表知道它什麼時候會被呼叫，以及前後需要哪些資料。

## 資料不確定夠不夠，先測既有 API

接著要確認新功能需要的資料從哪裡來。

我先反覆呼叫既有 API，對照回傳內容與原有程式的使用方式，理解欄位的用途，再確認這些資料能不能支援新需求。

主要看幾件事：

- 新功能需要的資料是否已經有回傳。
- 欄位原本代表什麼意思。
- 原有功能怎麼使用這些欄位。
- 放進新流程後，是否會影響原本的用途。

測試後發現，既有回傳欄位已經能提供這次前端功能需要的資料。

我再與 PM 討論沿用既有 API 的可行性與影響，最後確認能使用現有介面完成前端整合。

**這次沒有為前端整合額外擴充後端 API，但前面的資料確認還是要做。** 如果只看到某個欄位的值能用，就直接拿來接功能，很容易忽略它原本的用途。

## 相同需求，不同入口的執行順序不一定相同

這次整合時發現，不同操作入口雖然需要相近的資料，但資料取得時機與後續處理流程不一定相同。因此，除了確認 API 回傳內容，也需要追蹤資料何時被取得，以及後續程式如何使用。

我需要分別確認：

1. 各操作入口原本的執行流程。
2. 資料查詢在哪個步驟觸發。
3. 查詢後會執行哪些資料處理。
4. 新功能需要哪些資料，以及如何銜接後續處理。

確認各入口原本的執行順序後，再調整對應邏輯，讓查詢、資料處理與相關功能能正確銜接。

這個過程讓我更注意到：**需要的資料類型相近，不代表操作流程也相同。**

在既有系統裡擴充功能，除了看 API 回傳了什麼，也要追資料什麼時候取得、後面的程式又在什麼時候使用。

## 把需求整理成前端操作流程

理解資料與功能的關係後，接著需要規劃前端介面與操作方式。

前面確認過既有功能與資料來源後，我再把它們整理成使用者能操作的流程，完成相關畫面與功能：

- 依需求規劃新的操作介面。
- 取得並處理新功能需要的資料。
- 整合既有快照碼定位功能。
- 依不同操作入口調整執行順序。
- 將新的操作流程整合進原有介面。

完成初步實作後，再與 PM 確認功能是否符合需求。

這次前端需要處理的範圍，包含理解需求、確認資料是否足夠，以及決定功能應該如何接進既有流程。

## 沿用 API，也要留意欄位的用途

這次沿用既有 API，讓修改主要集中在前端，避免額外擴充後端介面及其相關整合工作。

不過，這不代表以後遇到新需求，都應該優先把既有欄位拿來用。還是要看欄位的用途是否符合需求，以及未來是否容易維護。

例如：

- 欄位原本的意思，是否與新功能需要的資料一致。
- 新功能是否依賴某種沒有明確約定的回傳格式。
- 後端調整欄位時，能不能找到新功能也有使用它。
- 如果兩個功能未來往不同方向發展，是否需要拆開。

這些是這次經驗後，我會進一步留意的維護問題。如果只是資料剛好長得像，但用途不同，就需要再與後端討論適合的做法。

## 做了哪些改善，哪些還不能下結論

這次完成了既有快照碼能力與前端功能的整合，也確認能在不額外擴充後端 API 的情況下，取得所需資料。

這次整合讓既有功能與資料能在新的操作情境中複用，避免重新開發相同能力。至於是否實際減少操作時間或提升作業效率，仍需要後續的使用數據才能確認。

另外，沒有修改後端 API，也不代表沒有回歸測試的需要。新增邏輯會進入既有流程，仍應確認不同入口的行為、原有定位功能，以及資料不足或查詢失敗時的處理。

## 這次學到的事

這次最花心力的地方，是在動手實作前，把既有功能、API 資料與操作順序對起來。

幾個我會記住的重點：

- **先追既有流程。** 知道函式做什麼，也要知道它何時執行、依賴哪些資料。
- **先確認資料，再決定是否擴充 API。** 是否能複用，需要看實際回傳與欄位用途。
- **不同入口要分別確認。** 相近的資料需求可能出現在不同的執行流程裡。
- **修改範圍小，也需要驗證。** 尤其是接進既有流程的邏輯，不能只看新畫面是否正常。

這次功能擴充讓我更理解，新增功能不一定需要從零開始。先從需求出發，看懂既有系統的執行流程，再確認哪些功能與資料可以複用，才能更有依據地決定修改範圍與實作方式。
