# 從 Vue 專案結構到前端架構設計：一個專案究竟可以拆分到多細？

剛開始接觸 Vue 時，我們通常會先從基本的專案結構開始：

- `components/`：存放元件
- `views/` 或 `pages/`：存放頁面
- `composables/`：存放可重複使用的邏輯
- `services/`：處理 API 請求
- `stores/`：管理全域狀態
- `utils/`：存放共用工具函式

這樣的結構對於剛開始開發的專案來說，通常已經足夠。

但隨著功能增加，專案可能不再只有幾個頁面與元件，而是逐漸出現不同的業務模組、資料管理、狀態處理與跨頁面共用邏輯。

這時候，原本單純依照技術類型分類的方式，可能開始遇到一些問題：

- 某些功能的程式碼散落在不同目錄。
- 一個頁面的邏輯逐漸變得複雜。
- 共用元件與業務元件的界線越來越模糊。
- 不同功能之間開始互相依賴。
- 修改一個功能時，可能需要同步調整其他地方。

這讓我開始思考：

**前端專案究竟應該拆分到什麼程度？又該如何判斷一個功能是否值得獨立管理？**

這篇文章會從 Vue 常見的專案結構出發，整理實際專案中觀察到的不同組織方式，並進一步探討 Feature、Component、Composable、Service 與 Store 的責任，以及模組拆分時需要考慮的事情。

---

## 1. 從學習階段常見的 Vue 專案結構開始

在 Vue 專案初期，通常會採用依照技術責任分類的方式：

```text
src/
├── assets/
├── components/
├── composables/
├── router/
├── services/
├── stores/
├── utils/
├── views/
├── App.vue
└── main.ts
```

這種結構有幾個優點：

1. 容易理解：每個資料夾都有明確的用途。
2. 容易查找：需要修改元件、API 或狀態時，可以直接找到對應目錄。
3. 初期維護成本低：不需要為每個小功能建立額外的目錄。

但當專案規模逐漸擴大，就可能遇到另一種情況。

例如：

```text
components/
├── Button.vue
├── UserTable.vue
├── UserForm.vue
├── PermissionDialog.vue
├── MapToolbar.vue
└── ReportChart.vue

composables/
├── useAuth.ts
├── usePermission.ts
├── useMap.ts
├── useReport.ts
└── useUser.ts
```

所有元件與 Composable 都依照技術類型集中管理。

這樣做並沒有錯，但當功能越來越多時，開發者可能需要在不同目錄之間來回尋找，才能理解某個功能的完整流程。

例如，要修改會員管理功能，可能需要同時找到：

- 會員相關元件
- 會員資料處理邏輯
- 會員 API
- 會員狀態管理
- 會員型別定義

這些程式碼雖然都屬於同一個功能，卻分散在不同地方。

因此，專案規模擴大後，就需要開始思考是否應該依照業務功能重新組織程式碼。

## 2. 實際專案中觀察到的不同組織方式

在實際接觸不同規模的 Vue 專案後，我發現專案結構不一定只有一種組織方式。

有些專案會以 `features/` 作為主要功能分類，有些則使用 `modules/`，也有些會保留以技術責任為主的共用目錄。

以下將觀察到的結構抽象化，僅保留資料夾層級作為示意，不代表任何特定專案的完整目錄。

### 架構示意 A：以 Feature 為核心組織功能

```text
src/
├── app/
│   ├── pages/
│   ├── layouts/
│   └── router/
│
├── features/
│   ├── auth/
│   ├── permission/
│   ├── member/
│   ├── map/
│   └── workflow/
│
├── components/
│   ├── common/
│   ├── table/
│   ├── form/
│   └── map/
│
├── composables/
├── services/
├── stores/
├── constants/
├── types/
├── utils/
└── styles/
```

這種方式會將具有獨立業務責任的功能集中在 `features/`。

每個 Feature 可以依照實際需求，管理自己的：

- Components
- Composables
- Services
- Stores
- Types

例如，權限相關的元件、邏輯與資料處理可以集中在 `permission/`，不需要全部散落在全域目錄中。

而 `components/`、`composables/`、`services/` 等目錄，則保留給跨功能使用的共用能力。

### 架構示意 B：以 Module 為核心組織功能

```text
src/
├── app/
│   ├── layouts/
│   └── router/
│
├── pages/
│   ├── home/
│   ├── system/
│   ├── report/
│   └── profile/
│
├── modules/
│   ├── auth/
│   ├── dashboard/
│   ├── workflow/
│   └── map/
│
├── components/
│   ├── base/
│   ├── responsive/
│   └── ui/
│
├── composables/
├── services/
├── stores/
├── constants/
├── types/
├── utils/
└── styles/
```

這種方式則會將頁面與功能模組分開管理。

`pages/` 主要負責頁面組成，而 `modules/` 則管理具有獨立功能責任的模組。

例如，頁面可以組合不同的模組，呈現完整的使用者操作流程。

另外，這類結構也可能依照桌面版、行動版或響應式需求，將 Layout 與頁面組織方式進一步拆分。

### 兩種方式有什麼差異？

| 比較項目 | 架構 A | 架構 B |
| --- | --- | --- |
| 主要分類 | Feature | Module |
| 頁面管理 | 集中於 app/pages | 獨立 pages |
| 功能管理 | features | modules |
| 共用元件 | components | components |
| 共用邏輯 | composables、services | composables、services |
| 組織思維 | 以功能為中心 | 頁面與功能分開管理 |

這兩種方式並沒有絕對的優劣。

需要特別說明的是，`Feature` 與 `Module` 並不是兩種具有固定標準差異的架構模式，也不是 Vue 官方規定的目錄名稱。不同團隊可能使用不同名稱，表達相近的功能組織方式。

因此，這裡比較的重點不是名稱本身，而是：

- 頁面與功能模組如何分工。
- 功能程式碼由誰管理。
- 共用能力放在哪裡。
- 模組之間如何建立依賴關係。

真正需要關注的不是資料夾叫什麼，而是每個模組是否具有清楚的責任，以及不同模組之間是否有合理的依賴關係。

## 3. Page、Section、Component 與 Feature 的責任差異

當專案開始拆分時，最容易遇到的問題就是：

**什麼東西應該放在 Page？什麼時候應該拆成 Component？又什麼時候需要獨立成 Feature？**

我會先從它們的責任來理解。

### Page：負責組合頁面

Page 通常對應一個路由或使用者可以進入的頁面。

它的主要工作是：

- 組合不同的元件。
- 管理頁面層級的資料。
- 處理頁面進入與離開的需求。
- 串接不同功能模組。

Page 不一定要負責所有業務邏輯。

如果一個 Page 裡面包含大量資料處理、狀態管理與操作邏輯，就可以考慮將部分責任移至適合的模組或 Composable。

### Section：負責頁面區塊

Section 通常是 Page 中具有獨立呈現目的的區塊。

例如：

- 搜尋區域
- 統計資訊區域
- 資料列表區域
- 圖表展示區域

當頁面內容變得複雜時，可以透過 Section 將不同區域拆開，讓 Page 更容易閱讀。

不過，Section 並不是每個專案都必須採用的層級，是否需要拆分仍然取決於頁面複雜度。

### Component：負責可重複使用的 UI

Component 主要負責介面呈現與使用者互動。

例如：

- Button
- Dialog
- Table
- Form
- Card

Component 可以是單純的 UI 元件，也可以包含一定程度的互動邏輯。

但如果元件開始承擔完整的業務流程，就需要重新思考它是否應該歸屬於某個 Feature。

### Feature：負責完整的業務功能

Feature 不只是將元件放在一起，而是將一個具有明確目的的功能集中管理。

例如會員管理功能可能包含：

- 會員列表
- 會員資料編輯
- 會員狀態管理
- 會員相關 API
- 會員資料型別

這些內容可能分散在不同技術類型中，但因為它們都服務於同一個業務功能，因此可以考慮放在同一個 Feature 裡。

簡單來說：

| 層級 | 主要責任 |
| --- | --- |
| Page | 組合整個頁面 |
| Section | 組織頁面區塊 |
| Component | 呈現 UI 與互動 |
| Feature | 管理具有獨立責任的業務功能 |

這些層級不是固定的階層規則，而是幫助我們思考程式碼應該由誰負責。

## 4. Composable、Service 與 Store 的責任如何區分？

除了元件與功能模組，Vue 專案還有幾個經常需要使用的程式碼組織方式。

### Composable：封裝可重複使用的邏輯

Composable 通常以 `use` 開頭，例如：

```ts
useAuth()
usePagination()
useWindowSize()
```

主要用途是封裝 Composition API 的邏輯，讓不同元件可以重複使用。

適合放入 Composable 的內容包括：

- 響應式狀態
- 生命週期處理
- 事件監聽
- UI 操作邏輯
- 可重複使用的互動邏輯

但並不是所有邏輯都應該放在全域 `composables/`。

如果某個 Composable 只服務於特定 Feature，而且與該功能高度相關，就可以考慮放在該 Feature 內部。

### Service：負責外部資料與服務介接

Service 通常負責與外部系統溝通，例如 API 請求。

```ts
export const getMembers = () => {
  return api.get('/members')
}

export const updateMember = (id: string, data: unknown) => {
  return api.put(`/members/${id}`, data)
}
```

將 API 請求集中管理，可以避免元件直接處理大量請求細節，也能讓資料介接方式更容易維護。

Service 不一定只能處理 HTTP，也可以依照專案需求負責其他外部服務介接。

### Store：負責跨元件或跨頁面的共享狀態

以 Pinia 為例：

```ts
export const useUserStore = defineStore('user', {
  state: () => ({
    user: null,
    permissions: []
  })
})
```

Store 適合管理需要在不同元件或頁面之間共享的狀態。

例如：

- 使用者資訊
- 登入狀態
- 權限資料
- 全域設定

但不是所有狀態都需要放進 Store。

如果狀態只在單一元件內使用，直接使用 `ref()` 或 `reactive()` 通常就足夠。

### 三者的差異

| 類型 | 主要責任 | 常見用途 |
| --- | --- | --- |
| Composable | 封裝可重複使用的邏輯 | UI、響應式邏輯、生命週期 |
| Service | 處理外部服務介接 | API、資料請求 |
| Store | 管理共享狀態 | 使用者資訊、權限、全域狀態 |

它們並不是互相取代的關係，而是依照不同責任分工。

## 5. Feature-based Architecture 與依照技術責任分類的差異

前面提到的兩種架構，其實反映了兩種不同的組織思維。

### 依照技術責任分類

```text
src/
├── components/
├── composables/
├── services/
├── stores/
├── types/
└── utils/
```

這種方式是依照程式碼的技術用途分類。

優點是容易理解，也適合規模較小的專案。

但當功能增加時，同一個業務功能的程式碼可能分散在不同目錄。

### 依照業務功能分類

```text
src/
├── features/
│   ├── auth/
│   ├── member/
│   ├── permission/
│   └── report/
│
└── shared/
    ├── components/
    ├── composables/
    ├── services/
    └── utils/
```

這種方式會先依照業務功能劃分模組，再將各功能需要的程式碼集中管理。

優點是當需要修改某個功能時，可以在相對集中的範圍內找到相關內容。

但也可能產生新的問題：

- Feature 數量過多。
- 功能邊界不清楚。
- 不同 Feature 之間互相依賴。
- 相同的共用邏輯被重複實作。

因此，Feature-based Architecture 並不是把所有東西都拆成 Feature，而是要判斷哪些功能真的值得獨立管理。

### 這與 Layered Architecture 有什麼不同？

另外，也常會看到 Layered Architecture（分層架構）的概念。

它主要是依照系統中的責任與依賴關係進行分層，例如：

```text
src/
├── presentation/
├── application/
├── domain/
└── infrastructure/
```

可以先簡單理解為：

| 層級 | 責任 |
| --- | --- |
| Presentation | 使用者介面與互動 |
| Application | 應用程式流程與使用案例 |
| Domain | 核心業務規則 |
| Infrastructure | 外部服務、資料來源與技術實作 |

Feature-based Architecture 與 Layered Architecture 並不是互斥的設計。

前者偏向依照業務功能組織程式碼，後者偏向依照責任與依賴關係分層。

在規模較大的系統中，也可能同時採用這兩種思維。

不過，並不是每個 Vue 專案都需要完整導入這樣的分層方式。

如果專案本身沒有足夠的複雜度，過度導入抽象層反而會增加理解與維護成本。

## 6. 我會如何判斷一個功能是否需要獨立成 Feature？

這是我在整理不同專案結構後，認為最值得思考的問題之一。

一開始，我會直覺地認為：

如果某個功能有超過兩個地方需要使用，就應該考慮將它獨立出來。

這個想法可以作為初步判斷的依據，但實際上，使用次數並不能完全決定一個功能是否適合成為 Feature。

例如，一個日期格式化函式可能被十個頁面使用，但它本身只是單純的工具函式，放在 `utils/` 就足夠了。

相反地，某個會員管理功能可能目前只有一個頁面使用，但它已經包含完整的資料管理、狀態處理與操作流程，也可能值得獨立管理。

因此，我會從以下幾個方向判斷。

### 6.1 使用範圍：是否有多個地方需要使用？

如果一個功能已經被兩個以上的頁面或模組使用，我會開始評估是否需要抽出來管理。

例如：

```text
pages/
├── dashboard/
├── member/
└── report/
```

假設這些頁面都需要使用權限判斷邏輯，就可以思考是否應該將權限相關的功能集中管理。

不過，這只是一個評估門檻，不代表只要被兩個地方使用，就一定要建立 Feature。

還需要確認它是否具有獨立的功能責任。

### 6.2 業務責任：是否具有明確且獨立的功能目的？

如果一段程式碼只是提供通用工具，例如：

- 日期格式化
- 數字格式化
- 字串處理
- 通用驗證函式

這些通常不需要獨立成 Feature。

但如果它代表一個完整的業務功能，例如：

- 會員管理
- 權限管理
- 登入驗證
- 工作流程管理

就可以考慮將相關內容集中在獨立的 Feature 中。

我認為這是判斷是否拆分時，相當重要的一個依據。

### 6.3 資料與狀態：是否有自己的管理需求？

如果一個功能開始擁有自己的資料、狀態與操作流程，就值得考慮是否需要獨立管理。

例如權限管理可能包含：

- 權限資料取得
- 權限狀態管理
- 權限規則判斷
- 權限異動操作

當這些邏輯逐漸分散在不同頁面或元件中，就可能增加維護難度。

將它們集中管理，可以讓權限相關的修改更容易被追蹤。

### 6.4 維護需求：是否需要獨立修改與擴充？

另一個我會考慮的方向，是這個功能是否有自己的變更需求。

例如，權限規則可能會隨著需求增加而持續調整。

如果每次修改都需要到不同頁面尋找相關邏輯，就代表目前的組織方式可能不夠集中。

這時候，將相關程式碼整理成獨立 Feature，就能讓後續維護更有範圍。

### 6.5 依賴關係：拆分後是否真的降低耦合？

最後，還要考慮拆分之後的結果。

如果建立 Feature 後，反而需要讓不同 Feature 大量互相引用內部實作，甚至出現循環依賴，那麼這次拆分可能沒有真正改善架構。

例如，假設兩個 Feature 之間出現以下依賴關係：

```text
member ──────> permission
   ↑               │
   └───────────────┘
```

這代表 `member` 依賴 `permission`，而 `permission` 又反過來依賴 `member`。

如果兩個功能彼此直接引用對方的內部實作，就可能形成循環依賴，也會讓模組之間的責任變得不清楚。

這時候就需要重新思考責任歸屬，可以考慮：

- 透過公開介面提供必要的功能。
- 避免直接引用其他 Feature 的內部實作。
- 將真正共用的能力移至 Shared。
- 重新確認資料與業務邏輯應該由哪個模組負責。

### 我的 Feature 拆分判斷原則

整理以上幾個方向後，我會這樣判斷：

| 判斷條件 | 我的處理方式 |
| --- | --- |
| 被兩個以上的地方使用 | 開始評估是否抽離 |
| 具有獨立的業務責任 | 強烈考慮獨立管理 |
| 有自己的資料與狀態 | 評估集中管理 |
| 有獨立的維護與擴充需求 | 考慮拆分 |
| 拆分後反而增加模組依賴 | 重新檢查責任邊界 |
| 只是通用工具或簡單共用邏輯 | 放在 Shared 或 Utils 即可 |

我不會把這些條件視為絕對的規則，而是作為評估依據。

**對我來說，真正值得獨立成 Feature 的，不是被使用最多次的程式碼，而是已經具有獨立責任，並且需要被獨立理解、維護與擴充的功能。**

---

## 7. 專案究竟應該拆分到多細？

理解不同的組織方式後，接下來還有一個問題：

是不是拆得越細，架構就越好？

我認為不是。

拆分的目的應該是讓程式碼更容易理解與維護，而不是單純追求目錄數量。

例如，一個簡單的功能可能只需要：

```text
features/
└── member/
    ├── components/
    ├── services/
    └── composables/
```

但如果只是為了一個小型功能，就再建立多層目錄：

```text
features/
└── member/
    ├── components/
    │   └── internal/
    │       └── shared/
    ├── application/
    │   └── use-cases/
    ├── infrastructure/
    │   └── repositories/
    └── domain/
        └── entities/
```

這不一定能帶來更好的維護性。

如果每個目錄都只有一個簡單檔案，而且責任沒有真正分離，就可能只是增加查找成本。

我會考慮以下幾個因素：

1. 功能複雜度：是否已經有足夠多的邏輯需要拆分？
2. 職責清晰度：不同程式碼是否具有不同責任？
3. 重複使用程度：是否有其他功能需要共用？
4. 維護需求：未來是否可能獨立修改或擴充？
5. 依賴關係：拆分後是否能降低耦合？

如果拆分後能讓責任更清楚、依賴更單純，而且不會增加太多理解成本，那麼這次拆分就有價值。

## 8. 過度抽象與耦合問題

在設計專案架構時，我認為有兩個方向都需要注意。

### 過度抽象

有時候我們會因為想讓程式碼更乾淨，就提前建立很多抽象層。

例如：

- 尚未出現重複需求，就先建立共用模組。
- 很小的功能也拆成多個目錄。
- 每個元件都建立獨立的 Composable。
- 為了符合某種架構模式，增加不必要的中間層。

這些做法不一定錯，但如果抽象本身沒有解決實際問題，就可能讓程式碼變得更難理解。

### 模組之間的耦合

另一個問題是模組之間的依賴關係。

即使每個 Feature 都有獨立目錄，也不代表它們之間沒有耦合。

例如：

```text
features/
├── member/
├── permission/
└── workflow/
```

表面上看起來已經分開，但如果 `member` 直接引用 `permission` 的內部實作，而 `permission` 又反過來依賴 `member`，就可能產生循環依賴。

因此，建立 Feature 後，還需要考慮：

- 哪個模組擁有這份資料？
- 哪個模組負責這項業務邏輯？
- 其他模組應該透過什麼方式使用它？
- 是否有真正共用的能力可以抽離？
- 是否出現不必要的雙向依賴？

一個好的模組邊界，不只是把程式碼放進不同資料夾，而是讓不同功能之間有清楚的責任與依賴方向。

### 資料夾結構不等於完整的系統架構

這點也是我在整理這篇文章時特別注意到的事情。

單純觀察資料夾結構，其實無法完整判斷一個專案的架構品質。

例如：

- 無法只靠資料夾判斷實際的 Import 依賴方向。
- 無法確認狀態是否由正確的模組管理。
- 無法判斷資料流是否合理。
- 無法確認是否存在循環依賴。
- 無法得知不同模組是否真的具有獨立責任。

因此，目錄結構只能作為理解專案組織方式的起點。

真正要評估架構，還是需要進一步閱讀程式碼、觀察模組之間的互動，以及了解功能變更時會影響哪些地方。

## 9. 這次學到的事

從一開始學習 Vue 時接觸的基本目錄結構，到後來觀察不同專案的組織方式，我逐漸發現，前端架構並不是單純決定要建立多少資料夾。

真正需要思考的是：

- 一個功能應該由誰負責？
- 哪些邏輯應該集中管理？
- 哪些程式碼適合共用？
- 不同功能之間應該如何依賴？
- 什麼時候應該拆分，什麼時候應該維持簡單？

我也開始理解，`Feature`、`Composable`、`Service` 與 `Store` 並不是為了讓專案看起來更有架構感而存在。

它們各自有不同的責任，應該依照實際需求使用。

尤其在判斷是否需要獨立成 Feature 時，不能只看一段程式碼被使用了幾次，而是要進一步考慮它是否具有獨立的業務責任、資料管理需求，以及後續維護與擴充的必要性。

對我來說，**好的專案架構不是拆得越細越好，而是讓每一段程式碼都有合理的位置，讓每個功能都能在清楚的責任範圍內被理解與維護。**

這也是我從單純完成前端功能，逐漸開始思考專案組織與工程維護時，對前端架構設計有更深一層的理解。
